### 1.1 구현 중 잡힌 것 두 건

| 발견 | 내용 | 조치 |
|---|---|---|
| `-0%` translate | `rectToTransform`의 첫 구현이 중앙 정렬 카메라에서 `-0`을 반환했다. CSS로는 유효하지만 단위 테스트가 `0`과 구분해 잡았다 | "중심이 프레임 중심으로 돌아오는 거리"로 식을 다시 써서 부호가 뒤집히지 않게 했다 |
| E-2의 잘못된 단정 | 처음에는 **끝** 사각형을 끌고 프레임 0의 transform이 바뀌는지 봤는데, 정상 동작에서는 바뀌지 않는다(프레임 0은 시작 사각형이다) | 시작 사각형을 끌어 프레임 0에서 검증하도록 수정. 테스트 쪽 결함이었고 앱은 옳았다 |

### 1.2 설계 문서에서 스스로 잡은 모순

초안 §2.3이 "프리셋 `zoomIn`은 현재 코드와 프레임 단위로 같은 결과를 낸다 — 회귀 판정의 기준선"이라고 썼는데, **D-01이 상한을 1.08 → 1.20으로 넓혔으므로 성립하지 않는다.** 같은 식이지만 폭이 커진다.

Plan §3.1 FR-M07과 §4.1 SC3의 "이전과 동일한 결과"도 같은 이유로 D-01과 양립하지 않는다. 설계 §2.3을 고쳐 지키는 범위를 좁히고, Plan의 해당 문구를 대체한다고 명시했다.

## 2. 기존 프로젝트에 생기는 눈에 보이는 변화

**저장된 루핑 프로젝트는 이 배포 후 모션이 더 커진다.** 의도된 변화이지만 조용히 일어나므로 여기 적는다.

| 강도 | 배포 전 (상한 1.08) | 배포 후 (상한 1.20) | 2.5초 홀드에서 1080px 폭이 움직이는 거리 |
|---|---|---|---|
| 0.4 | 1.032 | 1.080 | 35px → 86px |
| **0.5 (실사용)** | **1.040** | **1.100** | **42px → 108px** |
| 1.0 | 1.080 | 1.200 | 86px → 216px |

예전 폭이 필요하면 강도를 0.4로 내리면 1.08과 거의 같다. 모션의 **종류**는 보존된다 — `kenBurns: true`는 줌 인, `false`는 정지로 슬롯별로 그대로 옮겨진다(U-11·U-12).

## 3. 미결 — 이 환경에서 판정 불가

| # | 무엇 | 왜 불가 |
|---|---|---|
| E-4 | 프리셋 3종을 걸어 렌더한 MP4의 프레임 단위 방향·폭 (SC1) | H.264 인코더 없음 |
| E-5 | 드래그한 끝 영역이 홀드 마지막 프레임과 일치 (SC2) | 동일 |
| E-6 | 기존 저장 프로젝트가 같은 종류의 모션으로 렌더된다 | 동일 |
| 성능 게이트 | `npm run benchmark:render` 변경 전후 비교, NFR-M01(20% 이내) | 동일 |

**`KV_MOTION_MAX_SCALE = 3.0`은 그때까지 잠정값이다.** 상한을 넓힌 근거가 "1.08은 측정 없이 정해졌다"였으므로, 넓힌 쪽도 측정 없이 확정할 수는 없다. 게이트를 넘으면 좁힌다.

드래그 오버레이의 UI 동작은 E-2로 검증됐지만, 그 사각형이 실제 MP4 프레임과 픽셀 단위로 맞는지는 E-5에 달려 있다.
