## 변경 내용

`.editor`의 레이아웃 상수 한 줄(+ 근거 주석). 컴포지션·렌더 경로·도메인·컴포넌트 무변경.

처음에는 평문 `440px`로 적용했으나(§"1차 시도에서 드러난 제약") 좁은 창에서 스테이지 툴바를 침범해, 상한을 440으로 두고 그 아래에서는 툴바가 요구하는 폭을 먼저 보장하는 `clamp()`로 확정했다.

```
--inspector-width: clamp(320px, 100vw - 950px, 440px);
```

950px = 스테이지 왼쪽의 고정 비용 + 툴바 요구 폭(rail 60 + panel 296 + stage padding 28 + toolbar 566). 툴바에 컨트롤이 추가되면 이 상수를 옮겨야 한다.

## 실측 — 최종 상태

실제 CSS 기준(런타임 주입 없음). 괄호는 변경 전(320px 고정) 값.

| 뷰포트 | 인스펙터 | 패널 프리뷰 | 9:16 | 1:1 | 16:9 | 툴바 침범 |
|---|---|---|---|---|---|---|
| 1280×800 | 330 | 297×167 (287×161) | 281×499 | 499×499 | 566×499 | 없음 (−14px 여유) |
| 1366×768 | 416 | 383×215 (287×161) | **263×467 (263×467)** | 467×467 (467×467) | 566×467 (662×467) | 없음 (−14px) |
| 1512×945 | 440 | **407×229** (287×161) | **362×644 (362×644)** | 644×644 (644×644) | 688×644 (808×644) | 없음 (−75px) |
| 1920×1080 | 440 | **407×229** (287×161) | **438×779 (438×779)** | 779×779 (779×779) | 1096×779 (1216×779) | 없음 (−279px) |

- 패널 프리뷰: 1390px 이상에서 **287×161 → 407×229** (선형 +42%, 면적 2.02배). 16:9 소스는 레터박스 없이 박스를 꽉 채운다.
- 9:16·1:1 중앙 프리뷰는 **네 뷰포트 모두 변경 전과 완전히 동일**하다. 높이 제약이라 인스펙터 폭과 무관하다(Plan §3 예측대로).
- 남는 비용은 16:9 출력 하나뿐이며, 인스펙터가 실제로 넓어진 만큼만 줄어든다(1920 −10%, 1512 −15%, 1366 −14.5%, 1280 −2%).

폭에 따른 연속 변화(clamp 구간):

| 뷰포트 | 1280 | 1300 | 1340 | 1366 | 1390+ |
|---|---|---|---|---|---|
| 인스펙터 | 330 | 350 | 390 | 416 | 440 (상한) |
| 패널 프리뷰 | 297×167 | 317×178 | 357×201 | 383×215 | 407×229 |

1280~2560px 전 구간에서 툴바 침범 0, 툴바 압축 0(높이 48px 유지), 가로·세로 오버플로 없음, 인스펙터 필드 넘침 0.

## 1차 시도에서 드러난 제약 — 왜 평문 440px이 아닌가

평문 `440px`로 적용했을 때 좁은 창에서 스테이지 툴바가 인스펙터를 침범했다. 뷰포트 폭을 훑어 임계점을 특정했다.

| 뷰포트 (인스펙터 440 고정) | 툴바 | 상태 |
|---|---|---|
| 1280 | 530×51 | **침범 +60px** |
| 1300 | 530×51 | 침범 +40px |
| 1320 | 530×51 | 침범 +20px |
| 1340~1380 | 530~556×51 | 침범 없음, 툴바 압축(48→51px, 9:16 프레임 −3px) |
| 1390 이상 | 566×48 | 정상 |

같은 스윕을 320px에서 돌리면 1280까지 전부 정상이다. 즉 이 열화는 전적으로 440 상향이 만든 것이다.

원인: `.stage__toolbar`는 `justify-self: center`인데 자기 그리드 영역보다 넓어지면 스테이지 좌측 패딩에 붙고 초과분이 우측으로 흘러나간다. 툴바의 min-content는 530px, 자연 폭은 566px이라 스테이지 콘텐츠 폭이 566 미만이면 압축되고 530 미만이면 침범한다.

검토한 대안과 측정 비용:

| 대안 | 1280 침범 | 1366 툴바 | 1366 패널 프리뷰 |
|---|---|---|---|
| 평문 440 유지 | +60px | 51px (압축) | 407×229 |
| 툴바에 `flex-wrap: wrap; max-width: 100%` | 해소 | **90px (2줄)** → 9:16 프레임 −8% | 407×229 |
| 평문 400으로 하향 | 잔존(~1300 이하) | — | 367×206 |
| `@media (min-width: 1390px)` 로 440 게이팅 | 해소 | 48px | **287×161 (개선 없음)** |
| **`clamp(320px, 100vw - 950px, 440px)`** | **해소** | **48px** | **383×215** |

`clamp()`가 모든 축에서 우세하다. 침범과 툴바 압축을 동시에 없애면서, 1366의 9:16 프레임 −3px 회귀까지 사라지고(467 복구), 1280~1389 구간도 개선을 비례 배분받는다.

`100vw`와 스크롤바: `.editor`가 `height: 100vh; overflow: hidden`이라 문서 스크롤바가 생기지 않는다(실측 `h/v-overflow=false`). 따라서 클래식 스크롤바 환경에서도 `100vw == clientWidth`이며 950 상수가 어긋나지 않는다.

`.editor--panel-collapsed`(좌측 패널 접힘, `--panel-width: 0`)일 때는 스테이지에 296px이 더 생기므로 clamp가 보수적으로 동작한다 — 더 넓힐 수 있는데 안 넓힌다. 안전한 방향이라 그대로 둔다.

## 사용자 환경 실측 — 가정 두 개가 깨졌다

사용자 데스크톱(2560×1440, Chrome, `devicePixelRatio: 1`)의 콘솔 측정값:

```
viewport: 1103x1279   (DevTools 우측 도킹 상태)
outerWidth: 2560      screen: 2560x1440
inspectorPx: 320      trimBox: [272, 153]
source: [270, 480]
```

**1. Windows 클래식 스크롤바가 15px을 먹는다.** 헤드리스 측정은 287×161인데 실제는 272×153 — `.inspector__body`의 `overflow-y: auto` 스크롤바 폭만큼 차이난다. 계획서에 가능성으로만 적어둔 것이 확인됐다. 즉 440 상한에서의 실제 박스는 407이 아니라 **392**다.

**2. 실제 소재가 세로 영상이다.** `source: [270, 480]` = 정확히 9:16(원본 1242×2208). 계획 §3에서 "패널 소재는 통상 가로 영상이라 16:9 박스를 꽉 채운다"고 단정한 것이 틀렸다.

`inspectorPx: 320`은 DevTools가 폭을 1103으로 줄여 clamp이 바닥값을 준 결과다. `outerWidth: 2560`이므로 평소(DevTools 닫힘)에는 상한 440을 받는다 — **clamp은 손댈 필요가 없다.**

## 프리뷰를 렌더와 일치시키기

세로 소재를 16:9 박스에 `contain`으로 넣으면 폭의 68%가 검은 여백이고, 폭을 넓혀도 비율은 그대로다. 더 큰 문제는 렌더가 세로 소스를 패널 rect(1080×956)에 `cover`로 넣어 **세로 길이의 절반을 잘라내는데**, 프리뷰는 원본 전체를 보여줘 어느 절반이 남는지 알 수 없었다는 점이다.

`TrimStrip`에 옵트인 `framing` prop을 추가해, 주면 스테이지가 패널 슬롯의 비율을 갖고 미디어가 `SplitFrame`과 동일한 `cover` + `translate/scale`로 잘린다. 주지 않으면 기존 동작(16:9 + `contain`) 그대로다.

실측(뷰포트 2560, 인스펙터 440, 9:16 출력, 1242×2208 세로 소재):

| | 스테이지 박스 | aspect | fit | **실제 보이는 영상** | 면적 |
|---|---|---|---|---|---|
| 변경 전 | 407×229 | 1.778 | contain | 129×229 | 29,541 px² |
| **변경 후** | **407×361** | **1.129** | **cover** | **407×361 (박스 전체)** | **146,781 px²** |

**약 5.0배**. 스크롤바를 반영한 실제 사용자 환경 기준으로도 27,404 → 136,024 px²로 4.96배다. 인스펙터 폭은 건드리지 않았다.

출력 비율별로 패널 슬롯 모양을 따라가는 것도 확인했다:

| 출력 | 패널 슬롯 | 프리뷰 박스 | aspect |
|---|---|---|---|
| 9:16 | 1080×956 | 407×361 | 1.129 |
| 1:1 | 1080×537 | 407×202 | 2.011 |
| 16:9 | 956×1080 | 407×459 | 0.886 |

세 경우 모두 가로 오버플로 없음.

**크롭 일치 증명**: 위에서 아래로 8개 색 밴드(빨강→흰색)를 가진 1242×2208 세로 클립을 올리고, 인스펙터 프리뷰와 중앙 스테이지의 패널 A를 각각 캡처해 비교했다. 둘 다 가운데 4개 밴드(노랑·초록·시안·파랑)만, 같은 순서로 보여준다 — 프리뷰가 렌더와 같은 구간을 보여준다는 뜻이다. 변경 전 프리뷰는 8개 밴드 전부를 좌우 검은 여백과 함께 보여줬고, 그래서 빨강·주황·보라·흰색이 잘려나간다는 사실을 알 수 없었다.

**엔드카드는 무변경**: `framing`을 넘기지 않으므로 407×229 / 1.778 / `contain` 그대로임을 실측 확인했다. `TrimStrip`은 Day1 인스펙터의 두 호출부(패널 섹션, 엔드카드)에서만 쓰이고 3장면 인스펙터는 쓰지 않는다.

**자동 테스트 없음**: 이 변경의 결과는 전부 CSS 레이아웃이라 유닛 테스트로 잡히지 않는다(`day1-trim-ux.spec.ts` 주석의 "the strip needs a real <video>, a canvas, and layout"과 같은 이유). 스테이지 aspect와 `objectFit`을 단언하는 e2e를 추가할 수는 있으나, 이 컨테이너에서 e2e를 실행할 수 없어(§e2e) 검증되지 않은 테스트를 남기지 않았다. 위 측정은 모두 실브라우저 수동 검증이다.

## e2e — 실행 시도 결과: 브라우저가 막힌다

요청에 따라 `npx playwright test tests/e2e/day1-trim-ux.spec.ts tests/e2e/day1-trim-preview.spec.ts tests/e2e/day1-template.spec.ts`를 실행하려 세 경로를 시도했다.

**픽스처 문제는 해결됐다.** `apt-get install ffmpeg`로 libx264/aac가 있는 ffmpeg 6.1.1을 확보해 `npm run generate:editor-fixture`가 정상 동작했고, `gameplay-sample.mp4`·`day1-panel-b.mp4`·`endcard-2s.mp4`·배너/아이콘 png·코덱 픽스처 전부 생성됐다.

**남은 블로커는 브라우저 하나뿐이고, 이건 뚫리지 않는다.**

| 경로 | 결과 |
|---|---|
| `npx playwright install chrome` | 프록시가 `dl.google.com` 차단 — `curl: (56) CONNECT tunnel failed, response 403` |
| `npx playwright install chromium` (설정이 요구하는 v1234) | Chrome for Testing 151.0.7922.34 다운로드 실패 (CDN 차단) |
| 컨테이너에 있는 브라우저로 대체 실행 | Chromium **141.0.7390.37** — 오픈소스 빌드로 H.264가 없다 |

localhost(보안 컨텍스트)에서 측정한 코덱 지원:

```
canPlayType('video/mp4; codecs="avc1.42E01E"')   → "" (미지원)
MediaSource.isTypeSupported(avc1.42E01E)          → false
VideoDecoder.isConfigSupported(avc1.42E01E)       → false
VideoEncoder.isConfigSupported(avc1.42E01E)       → false
```

Day1 스펙은 H.264 mp4를 업로드해 디코드하고 mp4로 렌더하므로 이 브라우저에서는 통과할 수 없다. 실제로 돌려보면 업로드 직후 소스 메타데이터가 뜨지 않아 `uploadPanels`에서 죽는다(3 failed / 7 did not run, 전부 `day1-panel-a-metadata` 대기 타임아웃).

**이 실패가 이번 변경과 무관함은 대조 실행으로 확인했다.** 같은 브라우저에서 `editor.css`만 변경 전(`--inspector-width: 320px`)으로 되돌려 동일 테스트를 돌리면 **같은 지점에서 같은 이유로 실패한다**. 즉 환경 제약이며 회귀가 아니다.

`playwright.config.ts`의 `channel: 'chrome'`은 그대로 두는 것이 맞다 — 이 프로젝트 요구사항이 `chrome-only`이고, 오픈소스 Chromium은 애초에 지원 대상이 아니다. 컨테이너에 맞춰 설정을 고치는 것은 문제를 옮기는 것이다.

**남은 검증**: Chrome이 설치된 환경에서 위 명령 1회 실행. 픽스처는 `npm run generate:editor-fixture`로 만들면 되고(ffmpeg 필요), 그 외 사전 준비는 없다.
