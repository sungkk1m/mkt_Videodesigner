# Day1 Two-Video Render Spike

> Plan §4.3 Performance Gate 실측 결과
>
> **Date**: 2026-07-28
> **Verdict**: **PASS** — 게이트(≤ 1.50×) 대비 큰 여유. 정지 프레임 사전 추출 설계는 불필요.

## 질문

Day1은 활성 패널만 재생하지만, 정지된 패널의 첫 프레임도 디코더를 거쳐야 한다.
현재 단일 영상 렌더 대비 얼마나 느려지는가? 1.5배를 넘으면 정지 프레임을
`<Freeze>` 대신 사전 추출 이미지로 바꾸는 설계로 분기해야 한다.

## 방법

`spike.html` + `src/spike.tsx`(일회용, 측정 후 삭제)에서 `renderMediaOnWeb`을 직접
두 번 호출하고 벽시계 시간을 비교했다.

| 조건 | 값 |
|------|-----|
| 출력 | 1080×1920 · 60fps · 15초 (900프레임) |
| 코덱 | h264 / aac, `outputTarget: 'arraybuffer'`, `prefer-hardware` |
| 소스 | `tests/fixtures/gameplay-sample.mp4` (H.264 1920×1080 30fps 12초) |

- **baseline**: 전체 프레임 영상 1개 (현재 3장면 구조와 동일한 형태)
- **day1**: 상단 패널 재생 + 4px 분할선 + 하단 패널 `<Freeze frame={0}>` + `filter: grayscale(1)`

## 결과

| 실행 | baseline | day1 | 비율 |
|------|---------:|-----:|-----:|
| 1회차 | 11.26s | 10.83s | 0.96× |
| 2회차 | 10.57s | 10.67s | 1.01× |
| **평균** | **10.92s** | **10.75s** | **0.99×** |

## 해석

**Day1 구조는 사실상 무비용이다.** 두 가지가 겹친 결과로 본다.

1. 정지 패널은 프레임 1개만 디코딩하고 그대로 유지한다. 900프레임 내내 디코딩하는
   것이 아니다.
2. 각 패널이 출력 프레임의 절반 면적이라 스케일·합성 비용이 baseline의 전체 프레임
   1개와 비슷한 수준으로 상쇄된다.

`filter: grayscale(1)`도 측정 가능한 비용을 만들지 않았다. CTA 배경 블러가 이미
같은 경로로 검증된 것과 일치한다.

## 설계에 미치는 영향

- 정지 프레임 사전 추출(pre-extracted still) **설계 분기는 채택하지 않는다**. `<Freeze>` +
  `grayscale` 조합을 그대로 쓴다.
- Plan NFR "Day1 렌더가 기존 대비 1.5배 이내"는 **0.99×로 충족**. Check 단계에서
  재측정 대상으로만 남긴다.

## 한계

- 측정은 15초 9:16 한 조합, 2회 반복이다. 1:1·16:9와 60초는 미측정.
- 소스가 12초 H.264 1개다. 두 패널에 **서로 다른** 영상을 넣으면 디코더 인스턴스가
  2개가 되어 메모리 사용이 늘 수 있다. 이번 스파이크는 같은 파일을 두 번 참조했다.
