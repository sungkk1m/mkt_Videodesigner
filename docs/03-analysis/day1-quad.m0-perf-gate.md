## 1. 계획서의 M0을 그대로 돌릴 수 없었다

먼저 실측한 환경 제약이다.

| 항목 | 결과 |
|---|---|
| WebCodecs H.264 **인코더** (`avc1.42E01E` / `avc1.640028`) | **미지원** |
| WebCodecs H.264 **디코더** | **미지원** — 저장소의 H.264 픽스처를 소스로 쓸 수도 없다 |
| AAC 인코드/디코드 | 미지원 |
| VP8 / VP9 / Opus | 지원 |
| 실제 Chrome 설치 | 네트워크 정책이 `dl.google.com` CONNECT를 403으로 차단 |
| Playwright 번들 ffmpeg | 스트립 빌드 (`libvpx_vp8` · `png` · `webm`만). H.264 없음, ffprobe 없음 |

앱의 `probeRenderCapabilities`가 "H.264 인코더를 사용할 수 없습니다"로 렌더를 차단한다.
따라서 **`day1-render-speed.analysis.md`의 17.0초 기준선과 절대값을 비교하는 것은 불가능**
하고, 이 문서의 숫자는 전부 **같은 컨테이너 안에서의 상대 비율**이다.

### 1.1 그래서 무엇을 어떻게 쟀는가

| 항목 | 값 |
|---|---|
| 출력 | 1080×1920 · 30fps · **450프레임** · vp9/webm · `videoBitrate: 'high'` · `muted` |
| 구성 | **전부 패널 구간, 엔드카드 없음** — 패널 개수만이 유일한 차이가 되게 |
| 구간 | day1 `[225, 225]` / quad `[113, 113, 112, 112]` |
| 소스 | 1920×1080 8s VP9 WebM **4개, 서로 다른 파일** |
| 2패널 | **실제 `SplitFrame`** (복사 아님) |
| 4패널 | 스파이크 `QuadFrame`. `Panel`은 `SplitFrame`의 비공개 `Panel` 복사 |
| 반복 | 구성별 2회, **컨텍스트를 매번 새로** 만들어 디코더·비디오 캐시가 넘어가지 않게 |
| 기계 | 4 vCPU · 16GB · GPU 없음 · headless Chromium 141 |

소스를 4개 다른 파일로 만든 이유: Remotion 비디오 캐시가 `src`로 키를 잡아서 한 파일을
4번 쓰면 디코더를 공유해 **4패널 비용이 과소평가된다.**

`Panel` 복사본은 원본과 대조해 검증했다 (`artifacts/m0/verify-panel-copy.mjs`):
`Panel` 1,409자 · `PanelLabel` 529자 일치, 주석과 `export` 키워드만 제외.
복사가 틀리면 측정 자체가 무효이므로 이 검증이 전제다.

## 2. 4버킷 분해는 이 환경에서 쓸 수 없다

가장 먼저 드러난 것이다. 웹 렌더러가 찍는 `waitForReady` / `createFrame` / `addSample` /
`audioMixing` 네 버킷의 합이 렌더의 벽시계를 설명하지 못한다.

| 구성 | total | 4버킷 합 | 커버리지 |
|---|---:|---:|---:|
| day1-contain | 46,942ms | 12,943ms | **28%** |
| quad-contain | 54,087ms | 41,026ms | 76% |
| day1-cover | 22,000ms | 12,603ms | 57% |
| quad-cover | 25,218ms | 13,851ms | 55% |

같은 블러 작업이 변형에 따라 `createFrame` 안에 잡히기도 하고 밖으로 빠지기도 한다.
day1-contain은 시간의 72%가 버킷 밖이다 — 렌더러의 `waitForPageResponsiveness()`가
바쁜 메인 스레드를 기다리는 쪽으로 넘어간 것으로 보인다.

> **그래서 이 문서는 `createFrame` 배수를 인용하지 않는다.** 비교는 전부
> `renderMediaOnWeb` 호출을 감싼 벽시계(`totalMs`)다. 버킷은 참고로만 싣는다.
>
> 중간에 30프레임 스모크에서 `createFrame`이 524ms → 3,012ms(5.7배)로 보였는데,
> 워밍업이 섞인 데다 위 이유로 귀속이 틀린 값이었다. 450프레임 결과가 이를 뒤집었다.

`encode`(`addSample`)는 여섯 구성 전부 130~153ms로 사실상 상수다. 소프트웨어 VP9라
절대값은 이식 불가지만, **패널 개수와 무관**하다는 것만은 읽을 수 있다.

`decode`(`waitForReady`)도 6.0~7.5초로 거의 붙어 있다 — Q2 결정(재생 1개 + 나머지 정지)
덕에 동시 디코드가 1개로 유지되고, 정지 패널은 `Freeze`로 1프레임만 디코드하기 때문이다.
**패널을 4개로 늘려도 디코드는 늘지 않는다**는 것이 계획서 §2.3의 전제였고, 실측이 그것을
지지한다.

## 4. 읽어낸 것

**① 패널 개수는 문제가 아니다.** 2→4가 `cover`·`contain` 양쪽에서 정확히 1.15배다. 두
경로에서 같은 배수가 나온 것이 결과의 신뢰도를 높인다. Plan §7 **R1은 실측으로 기각**된다.

**② 비싼 것은 `contain`의 블러 배경이고, 그것은 4분할이 만드는 비용이 아니다.**
`cover`→`contain`이 day1 2.13배 · quad 2.14배 — 패널 개수와 무관한 고정 배수다.
**Day1은 이 2.13배를 오늘 이미 물고 있다.** day1-video 사이클이 기본값을 `contain`으로
바꿀 때 렌더 시간은 측정되지 않았고, 이 문서가 그 값을 처음 잰 것이다.

**③ 블러 배경은 프레임마다 다시 계산할 이유가 없다.** `SplitFrame`의 배경은 이미
`<Freeze frame={0}>` 정지 이미지이고 `blur(0.05 × 셀폭)`이 걸려 있다. 프레임마다 바뀌는
것이 없는데 렌더러는 450프레임 전부에서 블러를 다시 래스터화하고 비디오 요소를 다시
그린다. 블러를 비트맵에 구워 넣으면 두 비용이 함께 사라진다 — **day1 0.48배 · quad 0.52배.**

**④ 굽고 나면 `contain`이 사실상 공짜다.** `day1-baked` 22,639ms vs `day1-cover`
22,000ms — 차이 **2.9%**. 즉 배경을 구우면 "업로드는 무손실로 시작한다"(Q4)는 결정이
렌더 시간을 거의 요구하지 않는다. **Q4의 비용 근거가 사라진다.**

**⑤ 4분할이 오늘의 Day1보다 빠를 수 있다.** `quad-baked` 28,236ms vs 오늘의
`day1-contain` 46,942ms = **0.60배.**

## 5. 배경 굽기 — 후속 독립 사이클로 (2026-08-24 결정)

이 결과는 4분할이 만든 문제가 아니라 **Day1의 기존 비용**이고, 공용 코드 한 곳에서
고쳐지며 양쪽 템플릿이 함께 이득을 본다. 처음에는 그 성질만 보고 Plan §6 M1(공통 경로)에
넣는 것을 권고했는데, **사용자 결정으로 이번 사이클 범위에서 빼고 독립 사이클로 돌린다.**

그 판단의 근거:

- **4분할은 이걸 기다릴 이유가 없다.** 패널 개수는 1.15배로 이미 게이트를 통과했다.
- **M1의 다른 항목과 성격이 다르다.** 엔드카드 길이·파일명·드롭다운은 렌더 출력 픽셀을
  바꾸지 않아 기존 스위트가 그대로 게이트가 된다. 배경 굽기는 **픽셀이 바뀔 수 있어**
  시각 동일성 측정을 새로 붙여야 한다.
- **M1에 묶으면 4분할 전체가 그 리스크를 진다.** 블러 커널이 어긋나면 M1이 멈추고 뒤
  모듈이 다 대기한다. 분리하면 두 작업이 병렬로 간다.
- **선례가 있다.** `day1-render-speed`가 정확히 이런 종류의 렌더 최적화를 독립 PDCA
  사이클로 돌렸다 — 회귀식·PSNR/SSIM·프레이밍 동일성 증명 + crop 프록시 구현.
  규모와 성격이 같다.

아래는 그 후속 사이클을 위한 근거 기록이다.

구현 방향(설계는 그 사이클의 Design에서):

- 정지·재생 양쪽 배경 모두 대상이다. 배경은 어느 쪽이든 `Freeze frame={0}`이다.
- 굽는 시점은 소스가 붙고 프레이밍이 정해진 뒤 — `panelProxies`가 crop 프록시를 만드는
  자리와 성격이 같다. 렌더 직전 준비 단계.
- 흑백 배경은 별도 비트맵으로 굽는 편이 CSS `grayscale(1)`보다 싸다(이번 측정이 쓴 방식).

**미검증 — 반드시 확인해야 할 것:** 이번 스파이크는 ffmpeg `gblur`로 구웠고 CSS
`blur()`와 커널이 다르다. **픽셀 동일성은 검증하지 않았다.** 이건 성능 프로브였다.
배경은 화면에 보이는 요소이므로 후속 사이클이 시각 동일성을 먼저 확인해야 하며, 어긋나면
브라우저에서 한 번 블러해 비트맵으로 캐시하는 방식(커널이 같아진다)으로 바꿔야 한다.

시각 리스크의 실제 크기: 배경은 **`contain`이 남긴 여백에만 보인다.** 소스 종횡비가 셀과
같으면 전경이 셀을 꽉 채워 배경은 아예 보이지 않는다. 차이가 드러나는 조합은 "규격과 소스
방향이 어긋난" 경우로 한정되지만, 원본이 세로·가로 혼재라 그 조합은 실제로 발생한다.

## 6. 이 숫자를 어디까지 믿을 수 있는가

**믿을 수 있는 것 — 상대 비율.** 여섯 구성이 같은 기계·같은 소스·같은 프레임 수로
측정됐고, 구성별 2회의 편차가 215~3,985ms(0.9~7.4%)다. 1.15배와 1.5배 게이트 사이의
간격은 그 편차보다 훨씬 크다.

**믿을 수 없는 것 — 절대값.** H.264 대신 소프트웨어 VP9, GPU 없음, 4 vCPU.
`day1-render-speed.analysis.md`의 17.0초와 이 문서의 46.9초는 **비교 대상이 아니다.**

**비율에도 남는 편향:** 합성이 여기서는 완전히 CPU 바운드다. GPU가 붙은 기계에서는
블러 래스터화가 훨씬 싸므로 **②의 2.13배와 ③의 0.48배는 실제 기계에서 더 작을 수 있다.**
반대로 ①의 1.15배는 패널 개수에 대한 구조적 비용이라 덜 흔들릴 것으로 본다.

### 6.1 실제 Chrome에서 다시 돌리는 방법

```bash
npm install
npm run generate:editor-fixture       # H.264 픽스처 (실제 ffmpeg 필요)
npm run dev -- --host 127.0.0.1 --port 4173
```

그리고 `artifacts/m0/spike.tsx`에서 두 줄을 되돌린 뒤 `node artifacts/m0/run-gate.mjs`:

```diff
-    container: 'webm',
-    videoCodec: 'vp9',
+    container: 'mp4',
+    videoCodec: 'h264',
```

소스도 H.264로 바꿔야 한다 (`artifacts/m0/spike.tsx`의 `SOURCES`를
`tests/fixtures/*.mp4`로). `run-gate.mjs`의 `executablePath`는 지우면 로컬 Chrome을
쓴다. `M0_REPEATS=3` 권장.
