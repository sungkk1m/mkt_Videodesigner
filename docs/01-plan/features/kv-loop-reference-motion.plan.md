## 1. Overview

### 1.1 Purpose

영상팀 디자이너가 제시한 5개 항목을 루핑 템플릿의 동작으로 옮긴다.

### 1.2 Background — 요청 5개 항목의 해석

원문과, 그것이 이 코드베이스에서 무엇을 뜻하는지다. **이 절이 요청의 "무엇인지"에 대한 답이다.**

#### R-1. "each image should be slowly zoomed in and zoomed out before showing the next image"

**뜻**: 한 장이 화면에 있는 동안 카메라가 들어갔다가 **다시 나온다**. 다음 장으로 넘어가는 시점의 배율은 시작과 같다.

**지금**: [`resolveKvMotion`](../../../src/domain/kvloop/motion.ts)이 돌려주는 것은 `from` 사각형과 `to` 사각형 **두 개**뿐이고, [`KvScene`](../../../src/compositions/kvloop/KvScene.tsx)은 홀드 전체에 걸쳐 `from → to`를 한 번 보간한다. 편도다. 왕복하려면 진행도가 0 → 1 → 0으로 되돌아와야 한다.

**의미하는 변화**: 사각형 두 개는 그대로 두고, **진행도의 모양**만 램프에서 삼각파로 바꾼다. 줌 인·줌 아웃·팬 어느 프리셋이든 같은 한 줄로 왕복이 되고, 드래그로 지정한 사각형(`custom`)도 A → B → A로 자연스럽게 확장된다. 프리셋을 새로 추가하지 않는다.

#### R-2. "if the image duration is 2s, the maximum zoom in point should be at exactly 1s, before zooming out"

**뜻**: 정점은 홀드의 **정확히 절반**. 들어가는 시간과 나오는 시간이 같다(대칭).

**지금**: 정점이라는 개념 자체가 없다. 홀드 끝이 최대 배율이다.

**의미하는 변화**: 사용자가 초를 입력하는 항목이 새로 생기는 것이 **아니다**. 홀드 길이(`durationInFrames`)는 이미 `프리셋 ÷ 반복 ÷ 장수`로 정해져 있고, 정점은 거기서 자동으로 절반이다. 15초·3장·2회면 홀드 2.5초, 정점 1.25초.

한 가지 곁가지가 있다. 지금 이징이 `easeOut`이라 **정점에서 방향이 급반전한다** — 들어갈 때는 감속해 도착하지만 나올 때는 최고 속도로 튕겨 나온다. 왕복에서는 각 구간에 `easeInOut`을 걸어 정점 속도를 0으로 만들어야 "천천히 들어갔다 천천히 나온다"가 된다. R-1의 "slowly"가 이 부분이다.

#### R-3. "each transition should only be cut in, no fade in or out"

**뜻**: 장과 장 사이는 **컷**. 겹치는 구간도, 투명도 변화도 없다.

**지금**: `transitionMs` 기본값 400ms(=60fps에서 24프레임)로 항상 크로스페이드다. 스키마 하한이 `MIN_TRANSITION_MS = 100`이라 **0을 넣을 방법이 없다.**

**의미하는 변화**: [컴포지션은 이미 컷을 지원한다.](../../../src/compositions/KvLoopComposition.tsx) `transitionInFrames`가 0이면 세그먼트 연장(`+ transitionInFrames`)도 0이고 `fadeInFrames`도 0이라 `opacity`는 1로 고정된다. **막고 있는 것은 스키마의 하한값 하나뿐이다.** 컴포지션 코드는 건드릴 필요가 없다.

컷으로 바뀌면 부수 효과가 하나 있다. 지금은 홀드의 첫 24프레임이 크로스페이드 밑에 깔려 있고, `easeOut` 때문에 그 24프레임 안에서 이미 이동량의 41%가 끝난다(§1.3 표). 즉 **카메라 워크의 41%가 반투명한 상태로 소비되고 있다.** 컷이 되면 그 41%가 온전히 보이게 된다.

#### R-4. "add fade in gaussian blur effect at the start of the video, and add another gaussian blur fade out at the end"

**뜻**: 영상 첫 몇 프레임은 흐리게 시작해 선명해지고(블러 페이드 **인**), 마지막 몇 프레임은 선명한 상태에서 흐려지며 끝난다(블러 페이드 **아웃**). 검정 페이드가 아니라 **초점 이동**이다.

**지금**: 시작에는 아무 연출이 없다(첫 프레임부터 만 밝기·선명도). 끝에는 `fadeOutMs = 400ms`짜리 **검정** 페이드가 있다([`FadeOut`](../../../src/compositions/KvLoopComposition.tsx)).

**의미하는 변화**: 두 가지를 정해야 한다. ① 블러가 **무엇에** 걸리는가 — 키비주얼만인가, 타이틀 PNG·고지문구까지 포함한 화면 전체인가. "at the start of the video"라는 표현은 화면 전체를 뜻한다. ② 기존 검정 페이드와의 관계 — 대체인가 병존인가. 이 둘은 §1.4의 D-05·D-06이다.

#### R-5. "the duration of the blur should be approximately 10 frames, with the amount of blur set to approximately 30. this setting should be adjustable"

**뜻**: 블러 구간 길이 ≈ 10프레임, 블러 세기 ≈ 30, 둘 다 UI에서 조절 가능.

**따져야 할 것 둘**:

- **10프레임은 얼마인가.** 이 앱은 30fps와 60fps를 모두 렌더한다. 60fps에서 10프레임은 167ms, 30fps에서는 333ms다. 프레임 수로 저장하면 fps를 바꿀 때 체감 길이가 두 배로 달라진다. 나머지 시간 값(`transitionMs`, `fadeOutMs`)은 전부 ms다. → D-07.
- **30은 무엇의 30인가.** CSS `blur(30px)`은 표준편차 30px을 뜻하고, 1080px 폭에서는 화면 폭의 2.8%다(참고: `contain` 배경 블러가 5%). After Effects의 가우시안 블러 "Blurriness 30"은 이보다 훨씬 약해서 CSS로는 대략 10px에 해당한다. **어느 도구의 30인지에 따라 결과가 3배 차이 난다.** 디자이너가 "adjustable"을 붙인 이유도 아마 이것이다. → D-08.

### 1.3 Background — 현재 출력 실측

첨부된 `uavideo_kvloop_ko_9x16_15s_60fps.mp4`(1080×1920, 60fps, 900프레임, H.264/AAC)를 프레임 단위로 측정했다. 3장 × 2회 = 6세그먼트 × 150프레임이다.

**측정 방법**: 프레임을 270×480 그레이스케일로 내려 받아, 세그먼트 첫 프레임을 중심 기준으로 배율 *s*만큼 확대했을 때 대상 프레임과의 MSE가 최소가 되는 *s*를 0.002 간격으로 탐색했다(가장자리 영향을 피해 중앙 60%만 비교).

| 프레임 | 시각 | 실측 배율 | `easeOut` 이론값 | 비고 |
|---|---|---|---|---|
| 0 | 0.00s | 1.000 | 1.000 | 홀드 시작 |
| 24 | 0.40s | — | 1.041 | 크로스페이드 종료 지점 — 여기까지 이동량의 **41%** 소진 |
| 30 | 0.50s | 1.046 | 1.049 | |
| 60 | 1.00s | 1.078 | 1.079 | 이동량의 **79%** 소진 |
| 90 | 1.50s | 1.094 | 1.094 | |
| 120 | 2.00s | 1.100 | 1.099 | |
| 149 | 2.48s | 1.100 | 1.100 | 홀드 끝 |

읽히는 것 셋:

1. **총 이동량이 10%다.** 강도 0.5 × `KV_MOTION_MAX_PRESET_SCALE = 1.2` → 최대 1.100. 실측과 일치한다.
2. **마지막 1.5초 동안 23px 움직인다.** 1.079 → 1.100은 1080px 폭에서 23px, 초당 15px이다. 이 구간은 눈으로 정지 화면과 구분되지 않는다. 실제로 인접 프레임 차이가 0.00(255 스케일)인 프레임이 홀드당 27~32개 있다.
3. **보이는 이동은 1.041 → 1.100뿐이다.** 앞의 41%는 크로스페이드 밑에서 반투명하게 지나간다. 즉 관객이 온전히 보는 카메라 워크는 **총 10%가 아니라 5.9%, 64px**다.

전환과 앞뒤:

| 항목 | 실측 |
|---|---|
| 세그먼트 경계 | 인접 프레임 차이 최대 9.3/255 — 하드 컷 없음. 전부 400ms(24프레임) 크로스페이드 |
| 영상 시작 | 프레임 0의 평균 휘도 108.7로 곧바로 만 밝기. 오프닝 연출 없음 |
| 영상 끝 | 프레임 875(휘도 179.8)부터 899(휘도 1.0)까지 24프레임 = 400ms 검정 페이드 |

### 1.4 Background — 렌더러가 컨테이너 블러를 어떻게 다루는가

R-4는 화면 전체에 블러를 거는 요청이므로, `filter`가 **자식 요소까지** 도달하는지가 설계의 전제다. 지금 코드가 쓰는 유일한 블러는 `KvScene`의 배경 `<Img>` 하나 — 즉 **잎 노드**다. 컨테이너에 거는 것은 전례가 없다.

`@remotion/web-renderer@4.0.499` 번들을 읽어 확인했다.

| 확인 항목 | 결과 |
|---|---|
| `filterRequiresPrecompositing()` | `drop-shadow`가 포함된 경우에만 프리컴포지팅한다. `blur`는 `null`을 돌려준다 — 서브트리를 오프스크린에 모아 한 번에 흐리게 만들지 **않는다** |
| `setFilter()` 해제 시점 | `cleanupAfterChildren` 안에 있다. 즉 **자식을 그리는 동안 `ctx.filter`가 유지된다** → 컨테이너 블러가 서브트리에 도달하기는 한다 |
| 다만 | CSS의 "합성 후 블러"가 아니라 **요소별 블러**다. 요소가 겹치면 결과가 미세하게 다르고, 각 요소의 가장자리가 개별적으로 번진다 |
| 두 번째 경로 | Chrome 네이티브 `drawElementImage`(`html-in-canvas`)가 있으면 그쪽을 쓴다. 이 경로는 CSS 의미대로 동작하므로 **두 경로의 결과가 다를 수 있다** |

**결론**: 컨테이너 블러는 "된다"에 가깝지만 무료가 아니다. ① 프레임 가장자리에서 블러가 캔버스 색으로 번지므로 오버스캔이 필요하다(`BACKDROP_OVERSCAN = 1.2`과 같은 처리). ② 두 렌더 경로의 일치는 **실측으로 확인해야 한다** — 이것이 M0 스파이크가 존재하는 이유다.

| D-02 | 왕복 토글의 범위 | (a) 루프 전체 하나 (b) KV별 오버라이드까지 | **(a)** — 요청은 "each image"이고, 장마다 왕복 여부를 다르게 할 이유가 아직 없다. 필요해지면 모션과 같은 방식으로 확장한다 |
| D-03 | 왕복의 이징 | (a) 각 구간에 `easeInOut` 강제 (b) 프리셋의 이징 유지 (c) 사인 곡선 도입 | **(a)** — `easeOut`을 왕복에 그대로 쓰면 정점에서 튕긴다. 정점 속도 0이 "slowly ... and zoomed out"의 조건이고, 기존 `EASING` 맵을 그대로 쓴다 |
| D-04 | 컷을 어떻게 노출하는가 | (a) `transitionMs` 하한을 0으로 (0 = 컷) (b) 전환 방식 셀렉트(컷/크로스페이드) 신설 (c) 크로스페이드 제거 | **(a)** — `fadeOutMs`가 이미 "0 = 끔"이라는 선례다. 컴포지션은 그대로고 스키마 경계 한 줄이 바뀐다. 단 하한은 `kv-loop` 스키마 안에서만 낮춘다 (3장면이 공유하는 `MIN_TRANSITION_MS`는 건드리지 않는다) |
| D-05 | 시작·끝 블러가 걸리는 대상 | (a) 키비주얼만 (b) 타이틀·고지문구 포함 화면 전체 | **(b)** — 흐린 배경 위에 선명한 타이틀은 실수처럼 보인다. 고지문구가 흐려지는 구간은 앞뒤 각 10프레임뿐이다 |
| D-06 | 기존 검정 페이드아웃(`fadeOutMs`)과의 관계 | (a) 블러가 대체 — 새 프로젝트 기본값 0 (b) 병존 — 둘 다 기본값 유지 (c) 같은 구간에 겹침 | **(a)** — 요청문에 검정 페이드가 없다. 필드는 남겨 두고 **새 프로젝트 기본값만** 0으로 내려, 원하면 다시 켤 수 있게 한다. FR-L17("레퍼런스 두 편 모두 검정 페이드로 끝난다")과 정면으로 충돌하므로 확인이 필요하다 |
| D-07 | 블러 길이의 단위 | (a) ms (60fps 10프레임 = 167ms) (b) 프레임 | **(a)** — 30fps 렌더에서 길이가 두 배가 되는 것을 막는다. UI에는 "60fps 기준 약 10프레임"을 힌트로 병기한다. 컨벤션 §3.1은 둘 다 허용하므로 순수하게 fps 독립성 문제다 |
| D-08 | 블러 세기 "30"의 단위 | (a) CSS `blur(30px)` (b) After Effects Blurriness 30 ≈ CSS 10px (c) 프레임 폭 비율 | **(a)** — 값이 조절 가능하므로 첫 렌더를 보고 디자이너가 맞추면 된다. 기본 30px로 두되 **첫 검수에서 반드시 확인**한다. `kv-loop`는 9:16 전용이고 컴포지션 캔버스가 항상 1080×1920이라 px이 안정적이다 |
| D-09 | 시작·끝 블러 길이를 따로 두는가 | (a) 하나의 값을 양쪽에 (b) 각각 | **(a)** — 요청문은 하나의 길이를 말한다. 나누는 것은 나중에도 된다 |
| D-10 | 왕복 도입에 맞춰 모션 강도 기본값을 올리는가 | (a) 0.5 유지 (b) 올린다 (c) 첫 렌더 검수 후 결정 | **(c)** — 왕복은 같은 시간에 두 배 속도로 움직이므로 체감이 달라진다. 숫자를 미리 정하지 말고 실물을 보고 정한다 |
| D-11 | 레퍼런스 영상 확보 | (a) 요청문만으로 진행 (b) `mkt_looping reference` 폴더의 모닥불 루핑을 업로드받아 실측 후 설계 | **(b)** — 레퍼런스는 요청자 로컬(`C:\Users\...`)에 있어 이 세션에서 열 수 없었다. 왕복 폭·정점 유지 시간·블러 세기를 "근사"가 아니라 "일치"로 맞추려면 실측이 필요하다 |

## 4. Success Criteria

### 4.1 Definition of Done

| SC | 판정 방법 |
|---|---|
| SC1 | 렌더한 MP4에서 홀드별 배율 곡선을 §1.3의 방법으로 재면 1.00 → 최대 → 1.00 대칭이고, 정점 프레임이 홀드 중앙 ±1프레임 안에 있다 |
| SC2 | 홀드 경계에서 인접 프레임 차이가 홀드 내부 최대값보다 뚜렷하게 크다 (= 하드 컷이 검출된다). 크로스페이드 구간이 존재하지 않는다 |
| SC3 | 경계 직전·직후 프레임의 배율 차이가 1% 미만이다 (FR-R03) |
| SC4 | 첫 10프레임과 끝 10프레임에서 고주파 에너지(라플라시안 분산)가 단조 증가·감소한다. 나머지 구간에서는 변하지 않는다 |
| SC5 | 블러 구간의 프레임 가장자리 4변에서 캔버스 색 띠가 검출되지 않는다 (FR-R10) |
| SC6 | 저장된 기존 루핑 프로젝트를 열어 렌더한 결과가 변경 전과 프레임 단위로 동일하다 (FR-R12) |
| SC7 | 미리보기에서 스크럽한 프레임과 렌더된 같은 프레임이 일치한다 — 특히 블러 구간 (FR-R13) |
| SC8 | 기존 단위 테스트와 `tests/e2e/kv-loop.spec.ts`·`kv-motion.spec.ts`가 회귀 없이 통과한다 |

### 4.2 Performance Gate

`npm run benchmark:render`로 변경 전후를 측정한다. NFR-R02를 넘으면 블러 적용 지점을 컨테이너에서 잎 노드로 내리는 대안을 검토한다.

### 4.3 이 환경에서 판정 가능한 것과 아닌 것

| 판정 | 여기서 | 이유 |
|---|---|---|
| SC1·SC2·SC3 | ❌ | H.264 인코더가 없어 MP4를 만들 수 없다 |
| SC4·SC5 | ❌ | 위와 같음 |
| SC6 | ❌ | 위와 같음 |
| SC7 | 부분 | 미리보기 DOM의 `transform`·`filter` 문자열은 Playwright로 읽을 수 있다 (`kv-motion.spec.ts`의 `sceneTransform` 방식) |
| SC8 | ✅ | 단위 테스트와 코덱 불필요한 E2E |

**시스템 Chrome이 있는 기기에서의 렌더 검증이 이 사이클의 종료 게이트다.**

## 5. Risks and Mitigation

| 위험 | 영향 | 완화 |
|---|---|---|
| 컨테이너 블러가 두 렌더 경로에서 다르게 나온다 | 미리보기에는 보이는데 MP4에는 없거나 다르다 — 최악의 불일치 | M0 스파이크에서 두 경로를 각각 렌더해 비교. 다르면 잎 노드 적용으로 선회 |
| 블러가 프레임 가장자리에서 번져 검정 테두리가 생긴다 | 앞뒤 10프레임이 지저분해진다 | 오버스캔(`BACKDROP_OVERSCAN` 선례) + SC5 |
| `transitionMs` 하한을 전역으로 내려 3장면 전환이 0이 된다 | 다른 템플릿 회귀 | 하한을 `kvLoopSettingsSchema` 안에서만 낮춘다. `updateKvLoopSettings`의 `clamp`도 함께 (두 곳이다) |
| 왕복이 기존 강도 감각을 바꾼다 | "너무 빠르다/약하다" 재작업 | D-10을 첫 렌더 검수 뒤로 미룬다 |
| D-06이 FR-L17과 충돌한다 | 레퍼런스 해석이 갈린다 | 필드를 지우지 않고 기본값만 바꾼다. 되돌리기가 설정 하나다 |
| 스키마 변경이 저장 문서를 깨뜨린다 | 기존 프로젝트 유실 | `.default()` + SC6 |
| 이 환경에서 MP4 검증 불가 | SC1~SC6을 여기서 판정할 수 없다 | §4.3에 명시. 실기기 실행을 종료 게이트로 |

### 6.2 Current Consumers

- `transitionInFrames`를 읽는 곳은 `KvLoopComposition` 한 곳, 만드는 곳은 `buildKvLoopProps` 한 곳이다.
- `MIN_TRANSITION_MS`는 3장면(`sceneSchema.durationMs`, `SceneInspector`)과 공유된다 — **여기가 유일한 오염 경로다.**
- `KvMotionKeyframes`를 읽는 곳은 `KvScene`과 `KvLoopInspector`(사각형 시드) 둘이다.
- 타임라인·자산 해석·파일명은 모션도 전환도 모른다.

### 6.3 Verification

단위 테스트는 순수 함수에 집중한다 — 왕복 진행도(정점 위치, 대칭성, 경계 복귀)와 블러 ms → 프레임 환산. `domain/kvloop/motion.test.ts`의 기존 관례를 따른다. 컷 여부와 블러 DOM은 `kv-motion.spec.ts` 방식으로 스타일 문자열을 읽어 E2E에서 확인한다(코덱 불필요). 렌더 일치는 실기기 프레임 샘플링.
