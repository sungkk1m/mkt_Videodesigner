## 1. Overview

### 1.1 무엇을 만드는가

한 키비주얼 슬롯에 **이펙트 오브젝트 목록**이 생긴다. 오브젝트 하나는
"어디에(영역 또는 점) + 무엇을(이펙트 종류) + 어떻게(세기·색·밀도)"다.

지정의 두 경로:

| 경로 | 동작 | 근거 |
|---|---|---|
| **직접 지정** | 미리보기 위에서 영역을 드래그하거나 점을 찍는다. kv-motion-effects의 드래그 사각형 UX(`KvMotionOverlay`)가 전례이자 재사용 후보 | 확실하고, 모델 없이 동작한다 |
| **AI 지정** | 이미지에서 이펙트를 걸 만한 오브젝트(불, 광원, 하늘, 캐릭터 무기 등)를 감지해 후보로 제안하고, 사용자가 승인·수정한다 | browser-video-mvp Design의 "Optional intelligence — Beta 객체 감지"(미구현으로 남아 있던 자리)가 이 기능의 예약석이다. **AI는 제안까지만, 확정은 항상 사용자**로 두면 실패해도 직접 지정 경로가 남는다 |

### 1.2 이펙트 후보 — 레퍼런스에서 실측된 것부터

| 이펙트 | 레퍼런스 근거 | 구현 스케치 |
|---|---|---|
| 파티클 방출 (불티·반딧불·눈) | reference-measurement §3의 점 궤적 | 지정 영역에서 결정론적 시드로 방출, 캔버스에 프레임 함수로 드로잉 |
| 글로우 펄스 | §3의 방사형 halo | 지정 점 중심의 radial-gradient 레이어, 주기적 opacity/scale |
| 라이트 스윕 | 레퍼런스엔 없으나 UA 소재 관행 | `mask-image` + gradient — kv-motion-effects §1.2.2에서 렌더러 지원 실측됨 |

### 1.3 렌더 경로 — 이미 실증된 것과 스파이크로 확인할 것

- `@remotion/web-renderer`는 `<canvas>` 요소를 래스터화한다 (kv-motion-effects
  Plan §1.2.2 — `instanceof HTMLCanvasElement` 분기 실측). 캔버스 파티클 레이어는
  렌더에 들어간다.
- **M0 스파이크로 확인할 것**: ① `useCurrentFrame` 구동 + 시드 고정 파티클이
  미리보기·렌더에서 프레임 단위로 동일한가(결정론), ② 캔버스 레이어의 프레임당
  비용 — 북엔드 블러처럼 경로에 따라 비쌀 수 있다, ③ 두 래스터화 경로의 일치.

### 1.4 AI 지정의 기술 후보 (결정 전 조사 항목)

| 후보 | 성격 | 제약 |
|---|---|---|
| 온디바이스 세그멘테이션 (경량 SAM 계열·ONNX Runtime Web / transformers.js) | 클릭 지점 → 마스크. 서버 전송 없음 | 모델 수십 MB 로드, WebGPU 유무에 따른 속도 |
| 온디바이스 감지 (경량 디텍터) | 자동 후보 박스 | "불꽃" 같은 게임 아트 클래스는 일반 모델 밖 — 정확도 검증 필요 |
| 외부 vision API (옵트인) | 정확도 높음 | 소재가 기기 밖으로 나간다 — 기본값 불가, 명시 동의 필요 |

**직접 지정이 먼저 완성되고, AI는 그 위의 가속기**라는 순서가 이 표의 결론이다.
→ D-01로 확정. 이 절의 조사는 다음 사이클의 Plan으로 넘어간다.

## 3. Requirements

### 3.1 Functional

| ID | 요구사항 | 출처 |
|---|---|---|
| FR-O01 | 한 KV 슬롯에 이펙트 오브젝트를 0개 이상 추가·삭제할 수 있다 | §1.1 |
| FR-O02 | 파티클 오브젝트는 지정한 영역(0-1 프레임 좌표 rect)에서만 방출된다 | D-02 |
| FR-O03 | 글로우 오브젝트는 지정한 점·반경을 중심으로 주기적으로 밝아졌다 어두워진다 | D-02 |
| FR-O04 | 이펙트 프레임은 (스키마 값, 프레임 번호)의 순수 함수다 — 같은 프로젝트는 언제, 몇 번째 렌더든 같은 프레임을 낸다 | D-03 |
| FR-O05 | 이펙트는 슬롯의 카메라(왕복 줌·팬·직접 지정)와 함께 움직인다 | D-04 |
| FR-O06 | 영역·점·반경을 미리보기 오버레이에서 드래그로 편집할 수 있다 | D-06 |
| FR-O07 | 세기·색·밀도를 인스펙터에서 조절할 수 있다 | §1.1 |
| FR-O08 | 이펙트 없는 저장 프로젝트는 마이그레이션 없이 열리고 변경 전과 동일한 결과를 낸다 | 회귀 |
| FR-O09 | 미리보기에서 스크럽한 프레임과 렌더된 같은 프레임이 일치한다 | D-03 |

### 3.2 Non-Functional

| ID | 요구사항 |
|---|---|
| NFR-O01 | 이펙트가 없는 슬롯은 캔버스 레이어를 그리지 않는다 — 기존 프로젝트의 렌더 비용이 변하지 않는다 |
| NFR-O02 | 이펙트 켠 렌더 시간의 게이트는 실기기 측정으로 확정한다(D-05). 스파이크에서 컨테이너 상한을 먼저 실측한다 |
| NFR-O03 | 스키마 변경은 `.default([])` 방식으로, 기존 저장 문서를 파싱 실패시키지 않는다 |
| NFR-O04 | `domain`은 Remotion과 DOM을 임포트하지 않는다 — 파티클·글로우 수학은 순수 모듈이다 (conventions §1) |

| SC | 판정 방법 |
|---|---|
| SC1 | 지정한 영역에서만 이펙트가 발생한다 — 이펙트 on/off 렌더를 비교하면 영역(+글로우 반경) 밖 픽셀 차이가 코덱 노이즈 수준 이하 |
| SC2 | 같은 프로젝트를 두 번 렌더하면 프레임 단위로 동일 (결정론, FR-O04) |
| SC3 | 미리보기에서 스크럽한 프레임과 렌더된 같은 프레임이 일치 — 임의 프레임을 순수 함수로 단독 드로잉한 결과와 순차 렌더의 같은 프레임이 일치 (FR-O09) |
| SC4 | 이펙트가 왕복 줌과 함께 움직인다 — 정점 프레임에서 글로우 중심이 카메라 배율만큼 이동·확대 (FR-O05) |
| SC5 | 이펙트 켠 렌더 시간이 끈 렌더 대비 실기기에서 정한 게이트 이내 (D-05) |
| SC6 | 이펙트 없는 기존 프로젝트는 변경 전과 프레임 단위로 동일 (FR-O08) |
| SC7 | 기존 단위 테스트와 E2E가 회귀 없이 통과한다 |

### 4.2 이 환경에서 판정 가능한 것과 아닌 것

| 판정 | 여기서 | 이유 |
|---|---|---|
| SC1·SC2·SC3·SC4 | ✅ (VP9) | 수치 판정은 코덱 독립 — M0 스파이크가 VP9로 실증. H.264 최종 확인은 실기기 |
| SC5 | 부분 | 컨테이너는 소프트웨어 래스터라이저 상한 추정. 실기기 재측정이 진짜 판정 (블러 전례) |
| SC6·SC7 | ✅ | 단위 테스트 + 코덱 불필요 E2E |

**실기기 렌더 검증(M5)이 이 사이클의 종료 게이트다** — 이전 사이클과 동일.

## 5. Risks and Mitigation

| 위험 | 영향 | 완화 |
|---|---|---|
| 캔버스 드로잉이 래스터화 스냅샷보다 늦는다 (`useEffect` 타이밍) | 렌더에 빈/이전 프레임이 들어간다 — 최악의 불일치 | M0에서 순수 함수 드로잉 vs 인코딩 프레임을 수치 비교. 어긋나면 드로잉 시점을 바꾼다 |
| 캔버스 레이어의 프레임당 비용 | 북엔드 블러 전례: 소프트웨어 경로에서 프레임당 1.25초까지 | 파티클은 블러와 달리 전면 필터가 아니라 수백 개 점 드로잉 — M0에서 on/off 실측. 이펙트 없는 프레임은 레이어 자체를 그리지 않는다(NFR-O01) |
| 무작위성이 새어 들어온다 (`Math.random()`, `Date.now()`) | 스크럽·재렌더마다 다른 프레임 | 도메인을 순수 함수로 강제(NFR-O04), 결정론을 단위 테스트와 SC2로 고정 |
| 카메라 추종 시 파티클이 프레임 밖으로 번진다 | 가장자리 아티팩트 | `KvScene` 루트가 이미 `overflow: hidden` — 이미지와 같은 클리핑을 받는다 |
| 두 래스터화 경로(자체/네이티브)의 캔버스 처리 차이 | 미리보기와 실기기 렌더 불일치 | 캔버스는 픽셀 데이터라 필터보다 경로 민감도가 낮다 — 실기기 게이트(M5)에서 확인 |
| 스키마 변경이 저장 문서를 깨뜨린다 | 기존 프로젝트 유실 | `.default([])` + SC6 |

### 6.2 Current Consumers

- `KvSlotRenderProps`를 읽는 곳은 `KvScene` 하나, 만드는 곳은 `buildKvLoopProps`
  하나다 — 이펙트 프롭의 해석 지점도 같은 곳 하나여야 한다.
- `kvSlotSchema`는 `z.preprocess`(kenBurns 마이그레이션)를 감고 있다 — `effects`
  추가는 preprocess 뒤의 object에 `.default([])`로 들어가야 기존 문서가 그대로
  파싱된다.
- `KvMotionOverlay`는 `EditorWorkspace`에서 `selectedKvMotion?.kind === 'custom'`일
  때만 마운트된다 — 이펙트 오버레이도 같은 "편집 중일 때만" 규칙을 따른다.

### 6.3 Verification

단위 테스트는 순수 함수에 집중한다 — 같은 (시드, 프레임)이 같은 상태를, 다른
시드가 다른 상태를 내는지, 파티클이 영역+궤적 범위를 벗어나지 않는지, 글로우
주기가 프레임 수와 맞는지. 스키마 기본값과 커맨드는 `project.test.ts` 관례.
캔버스 내용은 DOM 문자열로 읽을 수 없으므로 E2E는 레이어 존재/부재와 transform
공유까지, 픽셀 판정은 M0 하네스와 실기기 게이트가 맡는다.

## 7. Module Breakdown

| M | 내용 | 검증 |
|---|---|---|
| M0 | 결정론 캔버스 레이어 스파이크 — 렌더 실증 | ① 2회 렌더 프레임 동일 ② on/off 프레임당 비용 ③ 영역 밖 무변화 ④ 카메라 추종 ⑤ 순수 함수 드로잉 = 인코딩 프레임 |
| M1 | 스키마·상수·커맨드·도메인 순수 함수 | 단위 테스트 |
| M2 | `KvScene` 캔버스 레이어 + 카메라 추종 | 단위 + E2E(레이어 존재·transform) + M0 하네스 재실행 |
| M3 | 인스펙터 목록·속성 + 오버레이 | E2E controls |
| M4 | 기본값 실측 — 레퍼런스에서 파티클 밀도·속도·크기·글로우 주기 측정, 검수 | 실측 문서 + 첫 렌더 검수 |
| M5 | 실기기 렌더 게이트 | SC1~SC7 + 성능 게이트 확정(D-05) |

M0이 실패하면(드로잉이 인코딩에 안 닿거나 비용이 감당 불가) 대안은 캔버스가
아니라 **DOM 노드 파티클**(개별 `<div>`/radial-gradient, 렌더러의 CSS 경로 활용)
— 스키마·도메인·UI는 동일하고 드로잉 계층만 바뀐다.
