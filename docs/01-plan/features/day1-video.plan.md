## 1. 결론: 코드 수정 없이 가능한가?

**항구적으로는 불가능하다.** 우측 패널 폭은 `src/features/editor/editor.css:9`의 `--inspector-width: 320px` 한 값이 전부이며,

- 인스펙터에는 접기/펼치기·리사이즈 핸들이 없다(좌측 패널만 `editor--panel-collapsed`로 접힌다 — `EditorWorkspace.tsx:177`),
- 폭을 저장하는 상태·localStorage·프로젝트 필드가 없다(`grep`으로 전 소스 확인),
- 설정 UI로 노출된 적도 없다.

**임시 우회는 있다 — 브라우저 확대(Ctrl/Cmd +).** 실측 결과:

| 확대율 | 뷰포트(CSS px) | 패널 프리뷰(물리 px) | 중앙 9:16 프리뷰(물리 px) | 비고 |
|---|---|---|---|---|
| 100% | 1920×1080 | 287×161 | 438×779 | 현재 |
| 110% | 1745×982 | 316×178 | 421×749 | |
| 125% | 1536×864 | **359×202** | 396×704 | 실용 상한 |
| 150% | 1280×720 | **431×242** | 354×629 | 타임라인·라벨이 답답해짐 |
| 175% | 1097×617 | 502×283 | 311×553 | **`.editor { min-width: 1280px }` 초과 → 가로 잘림** |

즉 확대는 프리뷰를 +25~50% 키워주지만, **우측 패널을 상대적으로 키우는 게 아니라 화면 전체를 키우는 것**이라 중앙 프리뷰와 타임라인을 같은 비율로 희생한다. 사용자가 말한 "디폴트 비율을 더 크게"는 코드 변경(=`--inspector-width` 기본값 조정)으로만 달성된다.

## 2. 왜 작은가 — 박스 계산 (실측)

```
인스펙터 320px
  − 좌측 보더 1px
  − .inspector__body  padding 14px ×2
  − .section__body    padding  2px ×2
= .trim__stage 폭 287px
  × aspect-ratio 16/9
= 287 × 161.4 CSS px          ← 패널 A/B 프리뷰 실측값
```

- 참고: 실측은 Chromium(오버레이 스크롤바) 기준이라 `scrollbar = 0`. 클래식 스크롤바 환경(Windows 등)에서는 여기서 약 15px 더 좁아진다.
- 패널 소스는 통상 가로 영상(e2e 픽스처도 1920×1080)이라 16:9 박스를 꽉 채운다. 즉 레터박스 문제가 아니라 **박스 자체가 작은** 문제다.

## 3. 실측 데이터 — 인스펙터 폭을 올리면 무엇을 잃는가

측정 방법: dev 서버 + Chromium에서 `--inspector-width`만 런타임 치환하고 `.trim__stage`·`.stage__frame` 경계 상자를 읽음. 코드는 변경하지 않음.

### 1920×1080

| `--inspector-width` | 패널 프리뷰 | 중앙 9:16 | 중앙 1:1 | 중앙 16:9 |
|---|---|---|---|---|
| **320 (현재)** | 287×161 | 438×779 | 779×779 | 1216×779 |
| 400 | 367×206 (+28%) | 438×779 | 779×779 | 1136×779 (−7%) |
| **440 (권고)** | **407×229 (+42%)** | **438×779 (동일)** | **779×779 (동일)** | 1096×779 (−10%) |
| 480 | 447×251 (+56%) | 438×779 (동일) | 779×779 (동일) | 1056×779 (−13%) |

### 1512×945 (MacBook 14")

| `--inspector-width` | 패널 프리뷰 | 중앙 9:16 | 중앙 16:9 |
|---|---|---|---|
| 320 | 287×161 | 362×644 | 808×644 |
| 440 | 407×229 | 362×644 (동일) | 688×644 (−15%) |
| 480 | 447×251 | 362×644 (동일) | 648×644 (−20%) |

### 1366×768 (하한 검증)

| `--inspector-width` | 중앙 9:16 | 중앙 16:9 |
|---|---|---|
| 320 | 263×467 | 662×467 |
| 440 | 261×464 (−0.6%) | 542×464 (−18%) |
| 480 | 261×464 (−0.6%) | 530×464 (−20%) |

**핵심 발견:** 중앙 프리뷰는 9:16·1:1에서 **높이 제약**(`.stage__frame { height: 100%; width: auto }`)이라, 인스펙터를 480px까지 넓혀도 **크기가 변하지 않는다**. 가로 여백만 줄 뿐이다. Day1 기본 출력이 9:16(`DEFAULT_RATIO`)이므로 이 변경의 실질 비용은 **0**이다.

**유일한 비용은 16:9 출력을 고른 경우** — 이때만 중앙 프리뷰가 폭 제약이라 인스펙터 증가분만큼 줄어든다(1920에서 −10%, 1366에서 −18%).

## 4. 옵션 비교

| # | 안 | 변경량 | 효과 | 비용/리스크 |
|---|---|---|---|---|
| **A** | `--inspector-width: 320 → 440px` 기본값 상향 | CSS 1줄 | 프리뷰 +42% (면적 2배) | 16:9 출력 시 중앙 프리뷰 −10~18%. 9:16/1:1은 손실 0 |
| B | 드래그 리사이즈 + 폭 저장(320~640 클램프) | 신규 스플리터 컴포넌트 + 상태/영속화 + 테스트, 약 80~120줄 | 사용자별 화면에 맞춤 | 상태·영속화 위치 결정 필요(localStorage vs 프로젝트 문서), 포인터 핸들러 e2e 추가 |
| C | 프리뷰만 확대(클릭 시 스테이지 위 오버레이 / "크게 보기" 토글) | TrimStrip + CSS, 약 40~60줄 | 레이아웃 불변, 필요할 때만 크게 | 모드가 하나 늘어남. 조정하면서 보는 흐름이 끊김 |
| D | 프리뷰 종횡비를 16:9 고정 → 패널 rect(9:16 출력 시 1080×956 ≈ 1.13:1)로 | TrimStrip CSS + props | 실제 렌더 모양과 일치 | **크기 문제는 해결 못 함** — `object-fit: contain`이라 가로 소스는 위아래 여백만 늘고 영상은 그대로 287×161 |

옵션 D를 크기 개선으로 오해하기 쉬워 명시해 둔다. D가 실제로 커지려면 `contain` → `cover` + 렌더와 동일한 scale/offset 트랜스폼을 프리뷰에 적용해야 하고, 그건 "프리뷰의 의미"를 바꾸는 별개 결정이다(§7 참고).

## 5. 권고

**A를 먼저, 단독으로.** 근거:

1. 사용자가 요청한 것이 정확히 "디폴트 폭/비율 상향"이다.
2. Day1 기본 출력 9:16에서 **측정된 손실이 0**이다. 트레이드오프가 사실상 없다.
3. 1줄 변경 · 되돌리기 1줄 · 신규 상태 없음. CLAUDE.md §2(최소 코드)·§3(외과적 변경)에 부합.

값은 **440px**를 권고한다. 480px도 1366×768까지 레이아웃이 깨지지 않지만, 16:9 출력의 중앙 프리뷰 손실이 −20%로 커진다. 440이 "프리뷰 면적 2배 / 16:9 손실 10%대"의 균형점이다.

B(드래그 리사이즈)는 A를 써본 뒤에도 화면별 편차가 남을 때 별도 사이클로 올리는 것을 권한다. 지금 함께 하면 요청 범위를 넘는 상태·영속화 결정을 끌고 들어온다.

## 6. Success Criteria (A안 실행 시)

- **SC1** `--inspector-width: 440px`에서 1920×1080 / 1512×945 / 1366×768 세 뷰포트 모두 가로 오버플로 없음(`scrollWidth <= clientWidth`), 인스펙터 내부 필드 줄바꿈 깨짐 없음 — 스크린샷 확인.
- **SC2** 9:16·1:1 출력의 중앙 `.stage__frame` 크기가 변경 전과 동일함을 실측으로 확인(회귀 방지).
- **SC3** 기존 유닛 스위트 + Day1 e2e(`day1-trim-ux`, `day1-trim-preview`, `day1-template`) 그린 유지.
- **SC4** `tsc -b` 통과.

## 7. Scope

**변경**: `src/features/editor/editor.css` — `--inspector-width` 기본값 1줄.

**Non-goals**: 드래그 리사이즈(옵션 B), 프리뷰 확대 오버레이(옵션 C), 프리뷰 종횡비/크롭 변경(옵션 D), 좌측 패널·타임라인 치수, 렌더 경로.

**별건으로 기록해 두는 관찰 (이번 범위 아님)**: 인스펙터 프리뷰는 소스 **전체**를 `object-fit: contain`으로 보여주는데, 렌더는 각 패널을 패널 rect에 `objectFit: 'cover'` + scale/offset 트랜스폼으로 **잘라서** 넣는다(`SplitFrame.tsx`의 `framing`). 즉 프리뷰에 보이는 화면과 실제 렌더 프레이밍이 다르다. 프리뷰를 키우면 이 불일치가 더 눈에 띌 수 있다. 별도 요청 시 다루는 편이 낫다.

## 8. Risks

| 리스크 | 대응 |
|---|---|
| 16:9 출력 사용자의 중앙 프리뷰 축소 | 실측치(−10%@1920, −18%@1366) 공유 후 폭 값 확정. 440 권고, 필요 시 400으로 하향 |
| 소형 화면(1366×768) 레이아웃 파손 | 실측상 440·480 모두 오버플로 없음. SC1로 재확인 |
| trim e2e의 `boundingBox` 단언 파손 | 해당 단언은 전부 상대값(윈도우 폭 자기비교, 트랙 비율 드래그)이라 절대 픽셀 의존 없음. 트랙이 넓어지면 `MIN_WINDOW_PX(34px)` 발동 가능성은 오히려 낮아짐. SC3로 확인 |

## 부록 — 2026-08-19 계획 수정 (실사용 데이터로 전제가 깨짐)

§4의 옵션 D를 "크기 문제는 해결 못 함"으로 기각한 근거는 **"패널 소재는 통상 가로 영상(e2e 픽스처도 1920×1080)"** 이었다. 사용자 환경에서 실제 소재를 측정하니 **1242×2208 세로 영상(9:16)** 이었고, 이 전제가 틀렸다.

세로 소재에서는 16:9 박스 + `object-fit: contain` 조합이 **폭의 68%를 검은 여백으로 쓴다**. 폭을 넓혀도 이 비율은 변하지 않으므로, §5에서 채택한 옵션 A만으로는 체감 개선이 제한된다.

추가로, 렌더는 세로 소스를 패널 rect(9:16 출력 시 1080×956, 가로형)에 `objectFit: 'cover'`로 넣어 **세로 길이의 약 50%를 잘라낸다**. §7에 "별건으로 기록해 두는 관찰"로만 남겼던 이 프리뷰/렌더 불일치가, 실제로는 프레이밍 판단을 불가능하게 만드는 주된 문제였다.

**수정된 결론**: 옵션 D를 `object-fit: cover` + 패널 rect 비율 + 패널 transform 형태로 확장해 채택한다(사용자 승인 2026-08-19). 실측 효과는 `docs/03-analysis/day1-video.analysis.md` §"프리뷰를 렌더와 일치시키기" 참조 — 인스펙터 폭을 더 건드리지 않고 실제 보이는 영상 면적이 약 5배가 된다.
