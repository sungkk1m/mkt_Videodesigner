## Executive Summary

| Perspective | Content |
|-------------|---------|
| **Problem** | Chrome이 디코딩하지 못하는 영상을 올리면 **에러가 나지 않는다.** 컨테이너는 정상 파싱되고 크기만 0x0으로 보고되기 때문에, 검증 코드가 "영상 트랙이 있는 파일을 선택하세요"라는 **사실과 다른 안내**를 띄웠다. 파일에는 영상 트랙이 있다. Chrome이 그 코덱을 못 읽을 뿐이다. 사용자는 있지도 않은 문제를 찾아 헤맸다. |
| **Solution** | 실패 경로에서만 ISO-BMFF 컨테이너의 sample-entry fourcc를 직접 읽어 **실제 코덱명을 담은** 에러를 낸다. 성공한 업로드는 이 비용을 전혀 내지 않는다. 동시에 "업로드 통과 = 렌더 통과"를 E2E로 고정해, 브라우저 코덱 지원이 바뀌어도 회귀를 즉시 잡는다. |
| **Function/UX Effect** | 거부 메시지가 "MPEG-4 Part 2 (DivX·Xvid) (mp4v)를 디코딩하지 못합니다"처럼 파일의 정체를 알려준다. HEVC(아이폰 촬영본·화면녹화)·VP9·AV1은 변환 없이 올라가며, 그 사실이 테스트로 잠긴다. |
| **Core Value** | 소재 준비 단계에서 **막히는 이유를 알 수 있게** 한다. 그리고 업로드 판정과 렌더 판정이 갈라지는 회귀를 자동으로 감시한다 — 편집을 다 끝낸 뒤 렌더에서 실패하는 상황이 이 사이클의 진짜 방어 대상이다. |

## 1. Background — 실측 근거

### 1.1 두 번의 측정

| 코덱 | 2026-07-28 (v0.1.0 근거) | **2026-08-01 Chrome 148 (실측)** | 현재 결과 |
|------|:---:|:---:|-----------|
| H.264 (avc1) | ✅ | ✅ | 정상 |
| HEVC (hvc1) — mp4 | `<video>` ❌ / WebCodecs ✅ | **양쪽 ✅** | **정상** (오거부 아님) |
| HEVC — .mov | 미측정 | **✅** | 정상 |
| HEVC — 10-bit | 미측정 | **✅** | 정상 |
| VP9 (vp09) | "사실상 오거부"로 추정 | **✅** | 정상 |
| AV1 (av01) | "사실상 오거부"로 추정 | 미검증 | 미확인 |
| VP8 (vp08) | "사실상 오거부"로 추정 | 미검증 | 미확인 |
| MPEG-4 Part 2 (mp4v) | ❌ | **❌** | 정거부 |

**v0.1.0의 전제 중 살아남은 것은 mp4v 한 줄뿐이다.** HEVC 오거부는 그 사이 Chrome이 해결했고, VP9는 애초에 되고 있었다. v0.1.0의 "사실상 오거부"는 측정이 아니라 `<video>`가 HEVC를 거부한다는 관찰에서 끌어낸 추론이었고, 그 추론이 틀렸다.

### 1.2 진짜 결함은 다른 곳에 있었다

mp4v 파일에서 Chrome은 **에러를 내지 않는다.** 컨테이너를 파싱하고 `loadedmetadata`를 정상 발화시키되 `videoWidth`/`videoHeight`를 0으로 보고한다. 그래서 이 파일은 `onerror` 경로가 아니라 **"영상 트랙이 없다"는 분기**로 떨어졌고, 사용자는 "영상 트랙이 있는 파일을 선택하세요"를 봤다. 그 파일에는 영상 트랙이 있다.

즉 이 사이클의 문제는 v0.1.0이 생각한 "판정 기준이 너무 좁다"가 아니라 **"판정이 틀렸을 때 하는 말이 거짓이다"**였다.

### 1.3 Mediabunny로는 풀 수 없었다

v0.1.0 §5는 "Mediabunny 파서로 메타데이터 추출을 대체하는 것이 이 작업의 실제 핵심"이라고 봤다. **불가능하다.** mediabunny는 자기가 지원하는 코덱만 모델링해서, mp4v를 파싱하려 하면 throw한다 — 정확히 우리가 이름을 알아내야 하는 그 파일에서 실패한다. WebCodecs `isConfigSupported()`도 답이 아니다. 그건 코덱 문자열을 **인자로 받는** API인데, 우리에게 없는 게 바로 그 문자열이다.

그래서 ISO-BMFF 박스 체인(`moov→trak→mdia→minf→stbl→stsd`)을 직접 내려가 sample entry의 fourcc를 읽는다. [codecTag.ts](../../../src/infrastructure/media/codecTag.ts) — 박스 헤더와 `moov`만 읽으므로 파일 전체를 훑지 않고, **실패 경로에서만 호출**되므로 성공한 업로드는 비용이 0이다.

## 2. Scope

### 2.1 In Scope

- 영상 업로드 실패 시 **실제 코덱명을 담은** 에러 메시지 — 완료 (`a2c1ff7`)
- 오디오 업로드도 동일 수준으로 — fourcc 리더를 오디오 trak까지 일반화하고 AAC·ALAC·AC-3 등 라벨 추가 (잔여)
- 업로드 통과 = 렌더 통과를 E2E로 고정 — HEVC 완료, AV1·VP8 잔여
- 판정은 런타임 위임을 유지한다. 코덱 화이트리스트를 우리가 들고 있지 않는다

### 2.2 Out of Scope

| 항목 | 사유 |
|------|------|
| ffmpeg.wasm 브라우저 내 트랜스코딩 (mp4v 대응) | 번들이 수십 MB 늘어 정적 경량 앱 기조와 충돌. 실제 mp4v 소재가 나올 때 재검토 (사용자 결정) |
| 서버 사이드 변환 | 무서버 원칙 |
| ~~검증을 WebCodecs `isConfigSupported()`로 이관~~ | **v0.2.0에서 폐기.** `<video>` 경로가 이미 렌더 경로와 같은 답을 낸다 (§1.1). 이관해도 얻는 게 없다 |
| ~~메타데이터 추출을 Mediabunny로 대체~~ | **v0.2.0에서 폐기.** 대상 파일에서 throw한다 (§1.3) |

## 3. Requirements

| ID | 요구사항 | 우선순위 | 현재 상태 |
|----|----------|:--------:|-----------|
| FR-M01 | HEVC mp4를 업로드·편집·렌더할 수 있다 | Must | ✅ 충족 — **브라우저가 해결.** 우리 몫은 회귀 감시 E2E |
| FR-M02 | VP9·AV1·VP8 영상을 업로드할 수 있다 | Should | ⚠️ VP9만 확인. AV1·VP8 픽스처 필요 |
| FR-M03 | 디코딩 불가 파일은 실제 코덱명과 사유를 담은 에러를 낸다 | Must | ✅ 충족 (영상) |
| FR-M04 | 업로드를 통과한 파일은 렌더도 통과한다 (판정 기준 일치) | Must | ✅ 충족 |
| FR-M05 | 기존 H.264 경로는 회귀 없이 동작한다 | Must | ✅ 충족 |
| **FR-M06** | 오디오도 디코딩 불가 시 코덱명과 사유를 담은 에러를 낸다 | Must | ❌ 미구현 |

> FR-M06은 v0.1.0 §2.1의 "오디오 업로드도 동일하게 점검"을 요구사항으로 승격한 것이다. 산문에 묻혀 있어 구현에서 누락됐다.

## 4. Success Criteria

| # | 기준 | 검증 | 상태 |
|---|------|------|:----:|
| SC1 | HEVC mp4 픽스처로 업로드 → 렌더 → `ffprobe` 확인이 통과한다 | E2E | ✅ [media-codec-compat.spec.ts:27](../../../tests/e2e/media-codec-compat.spec.ts) |
| SC2 | mp4v 픽스처가 코덱명(`MPEG-4 Part 2` + `mp4v`)이 포함된 에러로 거부되고, "영상 트랙이 있는 파일" 문구가 나오지 않는다 | E2E | ✅ 동 spec `:69` |
| SC3 | 기존 유닛 **287**개 · E2E **30**개 통과 | 회귀 | ✅ 2026-08-15 재실행 |
| **SC4** | AV1 mp4와 VP8 WebM이 업로드를 통과하고 **MP4까지 렌더된다** | E2E | ⏳ |
| **SC5** | Chrome이 디코딩 못 하는 오디오가 코덱명이 포함된 에러로 거부된다 | E2E | ⏳ |

> SC3의 기준선은 v0.1.0의 "164·17"에서 갱신했다. Day1 사이클(272·27)과 `a2c1ff7`을 거치며 늘어난 값이다.

**픽스처 생성 제약** (2026-08-15 확인):

| 픽스처 | 명령 | 비고 |
|--------|------|------|
| AV1 | `-c:v libsvtav1 -f mp4` | 정상 (`av01`) |
| VP8 | `-c:v libvpx -f webm` | **mp4 불가** — ffmpeg가 `Could not find tag for codec vp8 in stream #0`로 거부한다. VP8은 WebM에 담는다 |
| 오디오 거부 | `-c:a alac` (m4a) 우선 후보 | ALAC은 Chrome 미지원이고 Apple 생태계에서 실제로 나온다. 실패 시 `ac3`·`eac3`로 대체 — **어느 것이 실제로 거부되는지는 측정해서 고른다** |

## 5. Risks

| 위험 | 대응 |
|------|------|
| 브라우저 코덱 지원이 버전·하드웨어·OS별로 움직인다 | 우리는 화이트리스트를 들지 않고 런타임 판정에 위임한다. **이번 사이클이 그 증거다** — HEVC 지원이 우리 코드 변경 없이 생겼다. E2E가 그 변화를 감지하는 역할을 맡는다 |
| ~~메타데이터 추출 경로도 함께 바꿔야 함~~ | **v0.2.0에서 해소.** `<video>`가 0x0을 보고할 뿐 파싱은 되므로 길이·해상도 경로를 바꿀 이유가 없었다 (§1.2) |
| fourcc 리더가 컨테이너 형식에 결합된다 | ISO-BMFF 전용이고 WebM/Matroska에는 null을 반환한다. 호출자는 null을 "알 수 없음"으로 다루지 "영상 트랙 없음"으로 다루지 않는다 — 코드 주석에 명시 |
| fourcc 리더가 손상된 파일에서 크래시 | `try/catch`로 감싸 null 반환. 프로브 헬퍼가 디코드 실패를 크래시로 바꾸면 안 된다 |
| 기존 fingerprint·relink 로직 영향 | 파일 바이트 기반이라 코덱과 무관. 영향 없음 |

## 7. Next Steps

1. R1~R3 구현 — `/pdca do media-codec-compat`
2. `/pdca analyze media-codec-compat` — Plan ↔ 구현 Gap 분석 (Design 문서가 없으므로 Plan 기준 대조)
3. `/pdca report media-codec-compat`

**Design 단계를 건너뛰는 이유**: 영상 경로 구현이 이미 끝났고, 잔여 3건은 그 경로를 오디오로 확장하고 픽스처를 추가하는 작업이라 설계 선택지가 없다. 사후 Design 문서는 코드를 옮겨 적는 것에 그친다 (사용자 결정, 2026-08-15).
