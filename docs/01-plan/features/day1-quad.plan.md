## Executive Summary

| 관점 | 내용 |
|---|---|
| **Problem** | Day1 템플릿은 `panelA`/`panelB` 두 패널로 스키마가 고정돼 있어 "Before → After" 2단계만 보여준다. 성장·변화를 **DAY 1 → 7 → 14 → 30** 처럼 4단계로 끌고 가는 소재를 만들 수 없고, 2분할 영상 두 개를 외부 편집기에서 이어 붙여야 한다. |
| **Solution** | `template` 판별자에 `day1-quad` arm을 추가한다. 영상 4개를 2×2 그리드에 배치하고, 시간축은 `[패널 A, B, C, D, 엔드카드]` 5구간이 된다. 분할선·라벨·엔드카드·프록시·Batch는 Day1의 것을 **재사용**한다. |
| **Function/UX Effect** | 헤더 템플릿 선택기에 4번째 항목이 생기고, 애셋 패널이 영상 슬롯 4개, 인스펙터가 패널 4개 + 라벨 4개(×4언어)를 노출한다. 타임라인 경계는 4개가 되고 드래그 조작감은 동일하다. |
| **Core Value** | 이미 검증된 Day1 파이프라인(분할 기하 · 정지 프레임 흑백 · 엔드카드 자동 배치 · crop 프록시 · 4언어×3규격 Batch)을 그대로 쓰면서 서사 단계를 2 → 4로 늘린다. 새로 만드는 것은 **기하와 구간 수뿐**이다. |

## 1. Overview

### 1.1 현재 구조에서 무엇이 걸리는가

읽어서 확인한 사실만 적는다.

| 항목 | 현재 | 4분할에 쓸 수 있는가 |
|---|---|---|
| `sections` 축 | 가변 길이 `[2, 8]` (`constants.ts:MIN/MAX_SECTION_COUNT`) | **그대로 가능.** 5구간은 범위 안 |
| `expectedSectionIds(settings, count)` | 템플릿별 분기, 함수 형태 | **arm 하나 추가로 끝** |
| 타임라인(`timeline.ts`) | `SceneDurationsMs = readonly number[]`, 경계 드래그 N구간 일반화 완료 | **무변경** |
| `templateSettings` | `template`으로 discriminated union | **arm 하나 추가** |
| `day1PanelSchema` / `endCard` 스키마 | `day1SettingsSchema` 안에 인라인 | 공용 상수로 **추출 후 두 arm이 참조** |
| `splitLayout(ratio, lineWidthPx)` | 2분할 전용, `{a, b, line}` 반환 | 4분할용 `quadLayout()` **신규** |
| `activePanelForSection(0|1|2)` | `'a'|'b'|null` | 인덱스 → `'a'..'d'|null` **신규** |
| `SplitFrame.tsx`의 `Panel` | 내부 컴포넌트(비공개) | **파일로 추출해 두 컴포지션이 공유** |
| `EndCardScene.tsx` | 템플릿 무관 | **그대로 재사용** |
| Day1 명령 15종 | `Day1PanelKey = 'panelA'|'panelB'` 키 기반 | 키 유니언을 `panelC`/`panelD`까지 넓히면 **명령 코드 재사용** |
| `panelProxies.ts` | `PANELS` 리스트가 2개 하드코딩 | 리스트를 템플릿에서 받도록 **일반화** |
| `copy.day1Labels` | `{a, b}` (optional 필드) | `c`/`d`를 optional로 추가 → **마이그레이션 없음** |
| `MAX_BATCH_JOBS` / 파일명 / 자동저장 / JSON | 템플릿 무관 | **무변경** |

핵심: **`sections` 가변화(key-visual-looping 사이클)가 이미 끝나 있어서, 4분할은 스키마 버전을 올릴 필요가 없다.** `PROJECT_SCHEMA_VERSION`은 2에 머문다.

### 1.2 왜 별도 템플릿인가

`day1-template` Plan §2.2가 "영상 3개 이상, 가변 분할 개수"를 Out of Scope로 두면서
**"필요해지면 별도 템플릿으로"** 라고 적어 뒀다. 그 결정을 따른다. 근거를 다시 적으면:

- Day1은 PDCA 사이클이 **완료**된(Match Rate 100%) 템플릿이다. `panelA`/`panelB`를
  배열로 바꾸면 저장된 문서의 마이그레이션과 함께 완료된 사이클 전체가 다시 검증 대상이 된다.
- 반면 arm을 하나 더 두면 회귀 표면이 "공용으로 추출한 부분"으로만 좁혀지고,
  그 추출은 **동작이 아니라 위치만 바뀌는 순수 이동**이다.
- conventions §3.1이 명시한 규약과도 일치한다 — *"Adding a template means two arms,
  not a schema change."*

#### Q4의 파급 — `contain` 기본이 무엇을 뜻하는가

`contain`은 남는 자리를 소스 프레임 1장의 블러 사본으로 채운다(`SplitFrame.tsx`의
`BACKDROP_BLUR_RATIO`). 4패널 전부가 `contain`이면 **한 프레임의 video 요소가 최대 8개**
(패널 4 + 블러 배경 4)가 된다. 디코드는 여전히 "재생 1 + 정지 7(1프레임씩)"이라
Q2 결정 덕에 늘지 않지만, **합성 비용(`createFrame`, 렌더 시간의 25.2%)이 이번 사이클의
1번 리스크**가 된다. 그래서:

- **M0 성능 게이트는 `contain` 4패널, 즉 최악 구성으로 측정한다.** `cover` 구성으로
  측정하면 실사용보다 낙관적인 숫자가 나온다.
  > **측정 완료 (2026-08-24).** 패널 개수의 비용은 1.15배로 작았고, 비싼 것은 블러
  > 배경이었다 — `cover`→`contain`이 2.13배. **다만 배경을 비트맵에 미리 구워 넣으면
  > `cover` 대비 2.9%로 떨어진다.** 즉 Q4의 비용 근거는 배경 굽기(§6 M1) 여부에
  >달려 있고, 굽는다면 `contain` 기본은 사실상 무료다.
- 규격별로 셀 종횡비가 출력과 같으므로 **세로 원본을 9:16에 올리면 `contain`에서도
  블러가 사실상 보이지 않는다**(여백 0.25%). 즉 `contain` 기본의 비용은 "규격과 방향이
  어긋난 조합"에서만 실제로 발생한다.
- 패널별 Fit 토글은 Day1 인스펙터에 이미 있으므로 4패널로 확장만 하면 된다(§2.7).

## 2. 설계안

### 2.1 레이아웃 — 2×2 그리드

**왜 2×2인가.** 4분할 방식은 세 가지가 있는데, 셀의 종횡비가 결정적이다.

| 배치 | 9:16 셀 | 1:1 셀 | 16:9 셀 | 판정 |
|---|---|---|---|---|
| **2×2 그리드** | 537×957 (0.561) | 537×537 (1.000) | 957×537 (1.782) | **출력 비율과 사실상 동일** (오차 ≤0.25%) |
| 4행 스트립 | 1080×478 (2.26) | 1080×268 (4.03) | — | 초광각. 세로 캡처가 거의 안 보인다 |
| 1+3 히어로 | 비대칭 | 비대칭 | 비대칭 | 셀마다 프레이밍을 따로 잡아야 한다 |

2×2가 가진 성질 두 개가 그대로 이득이다.

1. **셀 종횡비 = 출력 종횡비.** `1080/2 : 1920/2 = 9:16`. 즉 9:16 출력에서 세로 캡처
   원본은 **crop 없이 셀을 꽉 채운다.** 현재 Day1의 9:16 패널은 1080×957(가로형)이라
   세로 소스의 절반을 버리는데(`day1-render-speed.analysis.md` §3: 디코드 픽셀의 49.8%만
   화면에 닿음), 4분할에서는 그 손실이 사라진다.
2. **규격 간 프레이밍 이식성.** 셀 비율이 규격마다 같으니 9:16에서 잡은 Scale/X/Y가
   1:1·16:9에서도 같은 구도를 준다 → 규격별 override를 덜 만지게 된다.

**기하 (분할선 6px 기준, `quadLayout(ratio, lineWidthPx)`)**

```
        col0   L   col1
      ┌──────┬─┬──────┐
 row0 │  A   │ │  B   │      L = lineWidthPx
      ├──────┼─┼──────┤      십자 분할선 = 세로 1 + 가로 1 = 사각형 2개
 row1 │  C   │ │  D   │
      └──────┴─┴──────┘
```

| 규격 | 출력 | col0 / col1 | row0 / row1 | 셀 종횡비 | 출력 종횡비 | 오차 |
|---|---|---|---|---|---|---|
| 9:16 | 1080×1920 | 537 / 537 | 957 / 957 | 0.5611 | 0.5625 | 0.25% |
| 1:1 | 1080×1080 | 537 / 537 | 537 / 537 | 1.0000 | 1.0000 | 0 |
| 16:9 | 1920×1080 | 957 / 957 | 537 / 537 | 1.7821 | 1.7778 | 0.24% |

`splitLayout`과 같은 규칙을 유지한다 — 나머지 픽셀은 뒤쪽 셀에 주어
`col0 + L + col1 == width`가 정확히 성립하게 한다(1px 이음선 방지).

**재생 순서는 읽기 순서** A(좌상) → B(우상) → C(좌하) → D(우하) — Q3 확정.

> 글로벌 기준 확인(2026-08-24): 레이아웃을 좌우 반전해야 하는 언어는 RTL 문자권
> — 아랍어·히브리어·페르시아어·우르두어 — 이고, 이 앱의 로케일 4종
> (`ko` / `en` / `ja` / `zh-TW`)에는 하나도 포함되지 않는다. 일본어는 만화의 칸
> 순서가 우→좌지만 그것은 만화 고유 관례이고, 현대 일본어 가로쓰기(横書き)는
> 좌→우다. 번체 중국어도 전통 세로쓰기는 우→좌지만 현대 가로쓰기는 좌→우다.
> **따라서 지금 로케일 집합에서는 Z 순서가 유일하게 맞는 선택이다.**
> 후속 고려: 아랍어 등 RTL 로케일을 추가하면 그리드를 좌우 반전해야 한다.
> `SPLIT_ORIENTATION`처럼 로케일별 매핑을 두면 되지만, 지금은 만들지 않는다.

### 2.2 시간축 — 5구간

```

```

`day1QuadSectionDurations(preset)`: 엔드카드가 초기값 3초를 먼저 떼고, 남은 시간을 4등분

| 15초 | 3,000ms | 3,000ms | `MIN_SCENE_MS`(1,000) 통과 |
| 30초 | 6,750ms | 3,000ms | 통과 |
| ~~60초~~ | — | — | **Q8a — 4분할에서는 제공하지 않는다** |

전부 **초기값**이다. 경계는 4개가 되고, `moveTimelineBoundary`는 이미 N구간 일반화가

새로 둔다. kv-loop이 `KV_LOOP_RATIO`로 규격을 9:16에 고정한 것과 같은 형태다.

- `DAY1_QUAD_PRESETS = [15, 30]` 상수를 두고 길이 프리셋 UI가 템플릿에 따라 목록을 좁힌다.

  변환**한다. kv-loop이 `selectedRatios`를 강제하는 지점과 동일한 코드 자리다.
- 전환 다이얼로그가 그 사실을 먼저 알린다 — kv-loop의 `template-switch-ratio-note`와
  같은 방식의 안내 문구 하나.

- **(b) 누적 점등** — 지나간 패널은 컬러 정지로 남기고 아직 안 온 패널만 흑백. 디코드

### 2.9 엔드카드 길이 제약 해제 (Q8b) — 조사 결과 이건 버그 수정이다

착수 전 코드를 열어 확인한 사실이다. **"엔드카드 길이 조정"은 신규 기능이 아니다.**

| 계층 | 현재 상태 |
|---|---|
| 타임라인 경계 드래그 | **이미 동작한다.** `moveBoundary`는 구간 수와 무관하게 일반화돼 있고 `MIN_SCENE_MS`(1초)만 강제한다. `DAY1_END_CARD_MS = 3000`은 **초기값**일 뿐이다 |
| 렌더 경로 | **이미 맞다.** `EndCardScene`은 실제 구간 길이(`durationInFrames`)를 받고, 소스가 짧으면 `loop`로 채운다 (Endcard-Video D-01) |
| 인스펙터 엔드카드 영상 트림 UI | **여기만 막혀 있다.** `maxLengthMs` · `playbackSlotMs` · 루프 채움 표시가 상수 3000ms를 슬롯 길이로 가정한다 (`Day1Inspector.tsx:605, 609, 681`) |
| `setDay1EndCardTrimLengthMs` | 트림 길이를 `DAY1_END_CARD_MS`로 clamp 한다 (`project.ts:1258`) |

즉 지금 Day1에서 엔드카드를 6초로 늘리면 **소스에서 3초 창까지만 고를 수 있고 나머지는
루프로 메워진다.** 사용자가 지정할 수 있는 길이와 UI가 가정하는 길이가 어긋난 상태다.

**수정 방향**: 상수 대신 **엔드카드 구간의 실제 길이**(`sections[last].durationMs`)를
읽는다. 인스펙터에 그 값을 내려주고, clamp 상한도 같은 값을 쓴다. `DAY1_END_CARD_MS`는
`day1SectionDurations` / `day1QuadSectionDurations`의 초기값 계산에만 남는다.

**Q8b 결정에 따라 Day1(2분할)도 함께 고친다.** Q10의 "Day1 무변경"에서 벗어나는 유일한
항목인데, 기능 추가가 아니라 기존 버그 수정이고, 분기를 두는 것보다 공용 코드 한 곳을
고치는 편이 싸다. **이 변경은 4분할 코드 0줄로 성립하므로 §6 M1에서 먼저 처리하고
기존 Day1 E2E가 회귀 게이트가 된다.**

### 2.12 블러 배경 굽기 (M0 발견 · 권고 · 결정 대기)

M0이 재고 나서야 보인 것이다. **`contain`의 블러 배경이 렌더 시간을 2.13배로 만들고,
그 비용은 4분할이 아니라 Day1이 오늘 이미 물고 있다.**

| 구성 | 450프레임 렌더 (같은 컨테이너) |
|---|---:|
| day1 `cover` | 22,000ms |
| day1 `contain` (**현재 기본값**) | **46,942ms** |
| day1 `contain` + 배경 굽기 | 22,639ms — `cover` 대비 **+2.9%** |
| quad `contain` | 54,087ms |
| quad `contain` + 배경 굽기 | 28,236ms — **오늘의 day1보다 빠르다 (0.60배)** |

**왜 고칠 수 있는가.** `SplitFrame`의 배경은 이미 `<Freeze frame={0}>` 정지 이미지이고
거기에 `blur(0.05 × 셀폭)`이 걸려 있다. 프레임마다 바뀌는 것이 하나도 없는데 렌더러는
450프레임 전부에서 블러를 다시 래스터화하고 비디오 요소를 다시 그린다. 블러를 비트맵에
구워 두면 두 비용이 함께 사라진다.

**왜 M1인가.** §2.9(엔드카드 길이)와 성격이 같다 — 4분할이 만든 문제가 아니고, 공용 코드
한 곳에서 고쳐지며, 양쪽 템플릿이 함께 이득을 본다. M1은 4분할 코드 0줄이라 기존 Day1
렌더 E2E가 그대로 회귀 게이트가 된다.

**Q4와의 관계.** 배경을 구우면 `contain` 기본(Q4)의 렌더 비용이 `cover` 대비 2.9%로
떨어진다. 즉 **"업로드는 무손실로 시작한다"는 결정이 성능을 거의 요구하지 않게 된다.**
굽지 않으면 Q4는 2.13배를 계속 물고 간다.

**미검증 — 이것이 결정 대기인 이유.** 스파이크는 ffmpeg `gblur`로 구웠고 CSS `blur()`와
커널이 다르다. **픽셀 동일성은 확인하지 않았다** — 성능 프로브였다. 배경은 화면에 보이는
요소이므로 렌더 출력이 미세하게 바뀔 수 있고, 그래서 "Day1 렌더 출력 무변경"(§3.2)에서
벗어나는 유일한 항목이 된다. 커널이 어긋나면 브라우저에서 한 번 블러해 비트맵으로
캐시하는 방식으로 바꿔야 한다(커널이 같아진다).

## 3. Scope

### 3.1 In Scope

**4분할 템플릿 본체**
- `day1-quad` 템플릿 arm (스키마 · 기본값 · 구간 ID · 명령 · 프리플라이트)
- `quadLayout` 2×2 기하와 십자 분할선
- `Day1QuadComposition` / `QuadFrame`, `Panel` 공용 추출
- 애셋 패널 4슬롯 · 인스펙터 4패널 · 라벨 4개×4언어(기본값 `Day1`/`Day2`/`Day3`/`Day7`)
- 길이 프리셋 15·30초 제약과 60초 프로젝트의 강제 변환
- `panelProxies` 4패널 일반화
- Day1 대비 렌더 시간 실측(M0 게이트)

**공통 경로 변경 — 4분할 코드 0줄, 기존 스위트가 게이트 (§2.9~2.11)**
- 엔드카드 길이 제약 해제: 상수 3초 → 엔드카드 구간의 실제 길이. **Day1 포함** (Q8b)
- 출력 파일명에 템플릿 세그먼트, **전 템플릿 일괄** (Q12) — 단정 6곳 수정
- 템플릿 선택기 세그먼트 버튼 → 드롭다운 (Q11) — E2E 헬퍼 추출, 10개 파일 수정
- **블러 배경 굽기, Day1 포함 (§2.12) — M0 발견, 권고, 사용자 결정 대기**
