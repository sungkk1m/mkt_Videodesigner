## 1. 무엇을 만들었나

"레벨 1에서 실패 → 레벨 20 → 레벨 99"의 성장 서사 광고 포맷. 구간마다 영상 한 편이
화면 상단을 채우고, 하단 검은 띠가 지금 몇 레벨인지 말한다. 레벨 1 구간은 **끝에서
반드시 FAIL 도장이 내리꽂히고**, 레벨 20 → 레벨 99 경계에서 화면이 줌 펀치로 넘어간다.

| 항목 | 값 |
|---|---|
| 템플릿 키 | `failure` · UI 표기 `실패(FAIL)` · 파일명 세그먼트 `fail` |
| 시간축 | `[panel-a, panel-b, panel-c, endcard]` 4구간 |
| 길이 | **30 · 60초** (15초 미제공, 전환 시 30초로 강제 변환) |

| 규격 | **9:16 · 16:9 전용** (1:1 미제공 — 스테이지·Batch 양쪽에서 비활성) |
| 방향 슬롯 | 구간마다 **세로용·가로용 소스를 따로** 보유(6슬롯). 9:16 렌더는 세로, 16:9 렌더는 가로를 쓰며 **자동 폴백 없음**(Q2) |
| 편집 방향 전환 | 미리보기 비율 토글이 곧 방향 토글 (D-1) — 새 UI 개념 없음 |

| FAIL 효과 | 구간 1 **끝에 앵커**된 1.5초 창(리드 0.5s + 스탬프 1.0s). 펀치 줌 2.2× · 탈색 · 스탬프 슬램(−8°) · 셰이크 · SFX, **다섯 가지 전부 개별 토글** |

| 엔드카드 | day1·quad와 완전히 동일 (스키마·컴포지션 공유, **신규 코드 0줄**) |

규모: 커밋 9개, 65개 파일 +8,131 / −754. 신규 소스 20개(컴포지션 4 · 도메인 6 ·

### 2.2 검증되지 않은 것 — 실기기 몫

**이 컨테이너의 Chromium에는 H.264 인코더도 디코더도 없다.** 이번 세션에서 직접 재확인했다:

| 확인 | 결과 |
|---|---|
| `VideoDecoder.isConfigSupported` avc1.42E01E / avc1.640028 | **false** (vp9 `true`) |
| `VideoEncoder.isConfigSupported` avc1.42E01E / avc1.640028 | **false** (vp9·vp8 `true`) |
| `canPlayType('video/mp4; codecs="avc1.42E01E"')` | **빈 문자열** |
| `MediaRecorder.isTypeSupported('video/mp4; …avc1…')` | **false** |

귀속을 코드가 아니라 코덱으로 확정하기 위해, **같은 업로드 컨트롤에 두 소스를 넣어**
비교했다:

- H.264 픽스처(`gameplay-sample.mp4`) → 앱이 정확히 거부한다:
  *"Chrome이 이 영상을 열지 못했습니다 (H.264 (avc1))."* → 메타데이터 없음
- VP9 소스(`m0-a.webm`) → 정상 처리: *"길이 8.00초 · 1920×1080 · 재생 디코딩 확인됨"*

`LEVEL 1`(x 349–716) → `LEVEL 20`(318–762) → `LEVEL 99`(318–761). 육안으로도 확인했다.
**엔드카드 구간에는 바가 없다**(설계 §6.3 구조 그대로).

**SC5 — 엔드카드**

27.000s에 정확히 시작해 3초간 유지된다. 다만 이번 렌더는 **소재가 들어가지 않은
상태**다 — §2.4.

### 2.4 이번 렌더에서 발견한 것 — 엔드카드가 비어 있다

마지막 3초가 균일한 `#0b0d10`(`CANVAS_COLOR`, 밝기 13.01·변화 0)이고 오디오도
−128dB(무음)다. 엔드카드 소재(배너 PNG 또는 엔드카드 영상)를 올리지 않으면 그 구간이
빈 캔버스로 렌더된다.

**코드 결함이 아니다.** day1·day1-quad도 동일하게 동작하고, 프리플라이트는 패널만
필수로 본다(엔드카드는 선택). 다만 **광고 소재로서는 마지막 3초가 검은 화면인 결과물이
나가므로**, 렌더 전에 엔드카드 소재를 넣었는지 확인해야 한다. 이 사이클의 범위를 넘는
판단이라 코드는 손대지 않았고, 필요하면 "엔드카드 비어 있음"을 프리플라이트 **경고**로
올리는 것이 다음 후보다(차단이 아니라 경고 — 의도적으로 비우는 사용도 가능하므로).

## 3. 만들었다가 잡은 결함 — 자동저장 손실 (이 사이클 최대 수확)

**증상.** failure 프로젝트에서 Batch 대화상자의 1:1 체크박스를 켜면 자동저장은
"저장됨"이라 말하는데, 새로고침하면 **빈 three-scene 프로젝트가 열린다.** 작업물이
아무 경고 없이 사라진다.

**원인.** M2에서 `refineFailure`에 "`render.selectedRatios`가 `FAILURE_RATIOS`를
벗어나면 거부"를 넣었다(Design §4.3). 그런데 `toggleRenderRatio`는 템플릿을 모르고
BatchDialog는 `ASPECT_RATIOS` 세 개를 그대로 체크박스로 내놓는다. 즉 **스키마가
거부하는 값을 UI가 만들어 낼 수 있었다.** 저장은 검증하지 않고 로드가 검증하므로,
다음 로드에서 `parseProject`가 실패하고 기본 프로젝트로 떨어진다.

Design §4.3이 정한 "3점 세트"(상수 + refine + `switchTemplate` 강제 변환)에 **네 번째
표면이 빠져 있었다** — 이미 그 템플릿 안에 들어와 있는 사용자가 비율을 고르는 곳.

**같은 구멍이 kv-loop에도 있었다.** `refineKvLoop`는 `selectedRatios`를 `[9:16]`으로
고정하는데, Batch에서 16:9를 켜면 똑같이 프로젝트가 날아갔다. **이 사이클보다 앞선
버그이고, 같은 수정으로 함께 닫혔다.**

**수정.** 지식을 한 곳에 두고 네 표면이 전부 그것을 읽게 했다 — `ratiosForTemplate()`
(`durationPresetsForTemplate`의 짝, 같은 파일). `toggleRenderRatio`·`setSelectedRatio`는
허용 밖 비율을 **거부**하고(교정하지 않는다), 이미 목록에 들어 있는 비율은 **뺄 수**
있게 남겼다 — 그러지 않으면 잘못 들어온 문서를 되돌릴 방법이 없다. BatchDialog와
스테이지 툴바가 같은 함수로 비활성 처리된다.

**회귀 방어.** 유닛 6건 + `verify-ratio-guard.mjs` 21건(3템플릿 × 2표면 × 새로고침 왕복).

> **교훈.** refine에 제약을 넣을 때는 **그 값을 만들 수 있는 모든 표면**을 같이 세야
> 한다. 저장이 검증하지 않고 로드만 검증하는 구조에서, 스키마가 거부하는 상태를 UI가
> 만들 수 있다는 것은 곧 **조용한 데이터 손실**이다.

## 4. 설계에서 달라진 것

### 4.1 사용자 결정으로 확정한 설계 수정 — D-12 (레벨 1의 펀치 아웃 제거)

**발견.** FAIL 비트와 레벨 1의 아웃고잉 펀치가 시간상 겹친다. Design은 둘을 각각
정의했다 — FAIL 창은 구간 1의 **마지막 1.5초**(D-3, 사용자 요구 "마지막 1초 고정"),
펀치 전환은 구간의 **마지막 0.25초**(§5.3). 30초 프리셋에서 구간 1은 162프레임이고
FAIL 창 117–161, 펀치 아웃 154–161 — **마지막 8프레임에 둘 다** 걸려 영상 레이어에
FAIL 줌 2.2배와 전환 줌 2.0배가 곱해져 순간 **4.4배**가 된다.

레퍼런스에는 이 상태가 없다(거기서는 FAIL이 9.6초 구간의 2.9–4.5초, 전환은 9.4–10.0초로
서로 떨어져 있다). FAIL을 구간 **끝**에 못 박은 것이 사용자 요구였으므로 구조적으로
붙을 수밖에 없었다.

**결정(사용자, 2026-08-28).** 레벨 1 → 레벨 20 경계를 **컷**으로 한다. 전환의 **양쪽
절반을 다** 뺐다 — panel-a의 out만 빼고 panel-b의 in을 남기면 앞선 줌인 없이 줌아웃만
남아 2배에서 튀어나오는 것처럼 보인다. 영상에 남는 펀치는 **레벨 20 → 레벨 99 하나**이고,
이는 레퍼런스의 두 번째 전환에 대응한다.

**검증.** 유닛은 상수가 아니라 **불변식**으로 적었다 — "구간 1의 모든 프레임에서
`zoomPunchAt`이 null". M4 게이트는 스탬프 폭 1.261(안착값)로 확인했다.

### 4.2 Design과 다르게 간 구현 5건 (결정은 하나도 뒤집지 않음)

| # | Design | 실제 | 근거 |
|---|---|---|---|
| 1 | `failStampStyleAt` → `blurPx` | `blurRatio` (프레임 폭 대비) | 도메인은 캔버스 크기를 모르고 9:16(1080)·16:9(1920)가 폭을 공유하지 않는다. `zoomPunchAt`이 이미 ratio를 반환해 규칙도 하나로 맞는다 |
| 2 | 스탬프 blur ∝ 스케일 **속도** | blur ∝ 남은 **이동 거리** | `easeIn`에 속도를 곧이곧대로 대면 **착지 순간 blur가 최대**가 되어 안착한 스탬프를 뭉갠다. 의도(진입 중에만 blur > 0)는 동일 |
| 3 | M1이 파일명·라벨·선택기 문구까지 | M2로 이월 | `TEMPLATE_FILE_SEGMENT`/`TEMPLATE_LABELS`가 `Record<TemplateKind, …>`라 kind 없이는 **컴파일이 안 된다**. M1의 게이트("failure 코드 0줄")가 더 강한 제약이라 그쪽을 지켰다 |
| 4 | M6이 렌더 arm | M4에서 함께 | `buildEditorSnapshot`에 arm을 넣는 순간 `EditorRenderRequest` 유니온이 컴파일 에러를 낸다. 커밋 사이에 빌드를 깨두지 않으려고 12줄을 앞당겼다 |
| 5 | `PanelSection` 추출은 순수 이동 | M5에서 `rect`를 prop으로 | failure 구간은 split도 grid도 아닌 영상 밴드 전체를 채운다. 어느 레이아웃에 속하는지는 호출자의 질문이라 계산을 Day1Inspector로 되돌렸다. M1 시점의 diff는 순수 이동이었다 |

## 5. SC7 — 효과의 렌더 비용

비교 대상은 **효과 켠 failure vs 효과 전부 끈 failure**다. day1과 비교하면 패널 개수
차이(day1은 프레임당 비디오 2개, failure는 1개)가 섞여 NFR-01이 묻는 것과 다른 질문에
답하게 된다. 컨테이너에 H.264 인코더가 없어 VP8/WebM으로 쟀고, `filter`·`transform`이
떨어지는 **컴포지트 버킷은 코덱 무관**이다. 벽시계 기준(M0의 교훈).

윈도우 측정(180프레임, 교대로 3회, 중앙값):

| 구간 | | 효과 ON | 효과 OFF | 오버헤드 |
|---|---|---:|---:|---:|
| `plain` (레벨 3 한복판 — 효과 0개) | Do 단계 | 62.46 ms/f | 63.12 ms/f | **−1.0%** |
| | 이번 세션 재측정 | 65.39 ms/f | 64.21 ms/f | **+1.8%** |
| `beat` (FAIL 비트 45프레임 + 펀치) | Do 단계 | 112.91 ms/f | 98.17 ms/f | +15.0% |
| | 이번 세션 재측정 | 88.80 ms/f | 74.22 ms/f | +19.6% |

**`plain`이 이 표의 핵심이다.** 두 번 재서 −1.0%와 +1.8%가 나왔다 — 부호가 뒤집힌다는
것 자체가 결론이다: **효과 창 밖 프레임에서 효과의 비용은 이 환경의 측정 잡음과
구별되지 않는다.** Design Goal 4("효과 밖 프레임의 스타일은 `undefined`")가 의도가
아니라 측정으로 확인됐다. quad가 상시 `filter`로 2.13배를 치른 그 자리다.

`beat`는 창 안 프레임이 34%뿐인 구간이고 부하에 따라 15~20%로 흔들린다. 30초 영상
900프레임 중 효과 프레임은 71개(7.9%)이므로 **영상 전체 기대치는 +3~4%**이고, 실제
900프레임 측정은 −4.8%였다(설정당 1회, ±5%는 이 조건의 실행 간 편차 안). 즉 30초
영상 전체로 보면 효과 비용이 측정 잡음보다 작다 — SC7의 "+15% 이내"를 만족한다.

> 재측정으로 Analysis §6의 `plain` −1%·`beat` +15%가 각각 +1.8%·+19.6%로 움직였다.
> 절대값을 인용할 때는 **이 컨테이너의 실행 간 편차가 ±5% 수준**이라는 점을 함께 봐야
> 한다. 신뢰할 수 있는 결론은 부호가 아니라 "창 밖 ≈ 0, 창 안은 유의미하게 비쌈"이다.

## 6. 검증 스크립트에서 잡은 것 — 거짓 실패 1건 (제품 결함 아님)

`artifacts/m1/verify-other-templates.mjs`의 마지막 단언(저장·복원 왕복)이 **3회 중 2회
실패**했다. 자동저장 손실 버그(§3)를 막 고친 직후라 그냥 넘길 수 없어 추적했다.

IndexedDB를 직접 폴링해 확정했다:

- 자동저장은 템플릿 전환 후 **595ms**에 `day1`을 기록한다 — 저장은 정상이다.
- 리로드 후 셀렉터는 **0ms에 `three-scene`, 100ms에 `day1`** 이다. 앱이 초기 프로젝트를
  먼저 그리고 IndexedDB 복원이 도착하면 교체하기 때문이다.

즉 스크립트가 `template-selector`가 보이자마자 값을 읽어 **복원 전 값을 잡은** 것이다.
Do 단계에서 고친 것은 **쓰기** 쪽 경합(리로드 전 대기 800→3000ms)이었고, **읽기** 쪽
경합이 남아 있었다. 복원값이 도착할 때까지 폴링하도록 고쳤고(도착하지 않으면 여전히
실패한다 — 단언의 취지는 유지), **3회 연속 그린**으로 확인했다.

`artifacts/m1/`의 다른 두 스크립트(`verify-quad-switch`·`verify-panel-move`)는 여전히
빨간데 **둘 다 이전 사이클에서 낡은 것**이고 이번 사이클과 무관하다(전자는 "선택기에
day1-quad가 아직 없다"를 단언, 후자는 `Panel.tsx`를 day1-quad M1 스냅샷과 글자 단위로
비교하는데 차이는 day1-label-effects가 넣은 주석이다). 남의 사이클 산출물이라 손대지
않았다 — 근거는 인수인계 문서에 있다.

## 7. 남은 작업

1. **실기기에서 E2E 자동 스펙 실행** — 결과물 검증은 §2.3으로 끝났지만, 회귀를
   자동으로 잡으려면 스펙 자체를 실기기에서 돌려야 한다.
   ```bash
   npm ci && npm run generate:editor-fixture && npx playwright test failure
   ```
   이 컨테이너에서는 불가하다(2026-08-28 확인): 커밋된 `playwright.config.ts`가
   `channel: 'chrome'`을 쓰는데 실제 Chrome이 없고, `npx playwright install chrome`은
   프록시가 `dl.google.com`을 막아 실패한다(`CONNECT tunnel failed, 403`). 컨테이너
   Chromium으로 우회해도 H.264 디코더가 없어 업로드가 필요한 3건은 막힌다(§2.2).
   참고로 `generate:editor-fixture`는 `codec-av1.mp4`에서 멈추지만(`libsvtav1` 없음,
   기존 사항) failure 스펙이 쓰는 픽스처 3종은 그 앞에서 생성된다.

   **엔드카드 소재를 넣은 렌더도 한 번 확인**하는 것이 좋다 — §2.4.
2. **실소재로 2.2× 펀치 줌 화질 확인 (R-3)** — 1080p 미만 소재에서 업스케일이 보이는지.

   day1/quad 공통 arm이 `panelA`·`panelB`만 missing으로 표시한다. 복원 경로가 뒤늦게
   `missing`으로 떨어뜨려 실사용 증상은 없고, failure arm은 여섯 슬롯을 전부 표시한다.
   **이번 범위 밖이라 고치지 않았다.**
