## 4. 실측이 바꾼 판단 두 가지

**① 축퇴 설계가 불필요해졌다.** 계획은 1.5배 초과 시 "정지 패널을 PNG로 사전 추출"을
예비안으로 뒀는데, 패널 개수 비용이 1.15배로 작아 그 복잡도를 도입할 이유가 없어졌다.

**② 프록시가 4분할에서는 덜 필요하다.** 2×2 셀이 출력 종횡비를 그대로 가지므로,
출력과 같은 방향의 소스는 `cover`에서 이미 거의 완벽히 맞는다. `planPanelProxy`가
`MIN_PROXY_SAVINGS`(20%) 아래로 판단해 트랜스코드를 건너뛴다 — 2분할에서는 세로 소스가
높이의 절반을 잃어 프록시가 항상 필요했던 것과 대조된다. 방향이 어긋난 소스(9:16에
가로 영상)에서는 여전히 68% 절약으로 프록시가 동작한다.

## 5. 브라우저 검증이 아니면 못 잡았을 결함

`useMediaSession.retain`은 목록에 없는 오브젝트 URL을 해제하는데, 워크스페이스가 그
목록에 `panelA`/`panelB`만 넣고 있었다. 4분할에서 **세 번째 패널을 올리는 순간 앞의
두 개가 해제되어 네 패널이 전부 "연결 필요"로 떨어졌다.**

유닛 테스트로는 잡히지 않는 종류다 — 도메인은 전부 옳았고, 증상은 세션 URL 수명에만
나타난다. Day1은 2패널이라 아무 증상이 없어서, **두 템플릿을 나란히 돌려 비교하고서야**
드러났다. 이 사이클에서 브라우저 검증이 값을 한 지점이다.

## 5.1 라이브 배포 검증에서 발견된 결함 (2026-08-26, build fd7ad18)

`main` 병합 직후 운영자가 실제 Chrome에서 4분할을 처음 만졌고, 컨테이너 검증이
놓친 결함 4건을 신고했다. 원인은 두 갈래였다.

**갈래 1 — `day1Of` 가드 잔존.** M3의 커맨드 이관이 패널 계열만 옮기고, 공유
필드 커맨드 6개(`updateDay1Split`·`updateDay1LabelStyle`·`updateDay1EndCard`·
`setDay1EndCardVideo`·`setDay1EndCardTrimInMs`·`setDay1EndCardTrimLengthMs`)는
`day1Of`인 채로 남겼다. 4분할에서 이들은 전부 조용한 no-op — **엔드카드는 영상
모드로 전환조차 되지 않아 업로드 입구가 막힌 것으로 보였다.** EditorWorkspace에도
같은 잔존이 넷: `renderableSource`가 3장면 arm으로 떨어져 **패널 4개를 다 올려도
렌더 버튼이 비활성**이었고, `unresolvedPanels`는 A·B 하드코딩, 타임라인
`onSelect`/`selectedId`는 클립 클릭을 3장면 경로로 보냈다(진단 로그의
"hook 선택됨"이 그 증상).

**갈래 2 — 섹션 경계 리마운트.** 섹션마다 별도 `<Sequence>`라 경계에서 다음
그리드 전체가 새로 마운트된다. `contain` 패널은 배경까지 비디오 2장이라 경계마다
최대 8개가 동시에 디코더를 새로 열었고, **패널 전환 시 프리뷰가 꺼졌다 켜졌다.**
Day1도 같은 구조지만 2장이라 티가 나지 않았다. `premountFor={fps}`로 다음 섹션을
1초 먼저 (opacity 0으로) 마운트해 완화했다.

왜 새어 나갔나: 유닛 테스트는 커맨드를 Day1 프로젝트로만 찍었고, 4분할 회귀
테스트는 패널 계열 커맨드만 덮었다. E2E는 이 경로를 정확히 찍었지만 컨테이너에
H.264가 없어 실행되지 못했다. 이번 수정에서 여섯 커맨드 전부에 4분할 회귀
테스트를 추가했고(옛 가드에서 실패함을 확인), 브라우저 검증
`artifacts/m1/verify-live-fixes.mjs` 9건이 전부 통과한다.

## 5.2 실기기 렌더 실측 (2026-08-26, 운영자 렌더 제공)

수정 배포(`c691b0a`) 후 운영자가 실제 Chrome(Windows)에서 렌더한
`day1x4_ko_9x16_15s_60fps` 출력물을 ffprobe/ffmpeg 픽셀 샘플링으로 검증했다.

| 항목 | 실측 | 판정 |
|---|---|---|
| 컨테이너 | h264 + aac, 1080×1920, 60fps, 14.98s | SC1(9:16) ✅ |
| 용량 | 19.7MB (60fps·15s) | Q14(≤52MB) ✅ |
| 흑백 유지 | t=0.5s: A(재생) 채도 0.153 / B·C·D(유휴) 정확히 0.000 · t=7.5s: C(재생) 0.091 / A(유휴) 0.000 | SC3 ✅ |
| 분할선 | 세로 (152,161,175) · 가로 (156,160,168) vs 설정값 #9CA3AF=(156,163,175) — 인코딩 오차 이내 | SC4 ✅ |

E2E의 재생 패널 채도 임계값(>0.25)은 테스트 픽스처 기준이고, 운영자의 저채도
게임 화면은 0.09~0.15로 그보다 낮다 — 유휴 0.000과의 구분은 명확하므로 판정에는
지장이 없지만, 실소재 기준으로는 임계값이 공격적이라는 기록을 남긴다.

같은 세션에서 스크럽 문제의 실체도 확정됐다: 포인터 이동마다 Player 시크가
실행되고, 4분할 시크 1회는 최대 8개 비디오 재디코드라 무거운 소스에서 메인
스레드가 포화되어 **드래그 내내 화면이 갱신되지 않다가 릴리즈 때 한 번에
반영**됐다. 빨간 선·타임코드는 매 이동마다 즉시 갱신하고 Player 시크만 150ms
스로틀(마지막 프레임 보장)로 분리해 해결 — `verify-scrub-realtime.mjs` 5건 통과.

### 5.2.1 남은 실측 완료 (2026-08-26, build `3afe45b`)

운영자가 30초 렌더와 Day1(2패널) 렌더의 진단 로그를 제공해 남은 항목이 모두
닫혔다.

**규격·용량**

| 항목 | 실측 | 판정 |
|---|---|---|
| 9:16 | 렌더 완료 (15s 19.7MB / 30s 42.2MB) | SC1 ✅ |
| 1:1 · 16:9 | 둘 다 렌더 완료 | SC1 ✅ **3규격 완결** |
| 30초 용량 | 43,208KB = **42.2MB** (60fps·standard) | Q14(≤52MB) ✅ |

15초 19.7MB → 30초 42.2MB는 2.14배로, 길이에 대해 거의 선형이다. 다만 상한
대비 **여유가 19%(9.8MB)뿐**이므로, 이보다 움직임이 많은 소재를 30초·60fps로
뽑으면 상한을 넘을 수 있다. 넘을 경우의 대응은 fps를 30으로 내리는 것이다
(프레임 수가 절반이므로 용량도 대략 절반).

**렌더 시간 — 패널 2개 vs 4개**

같은 Windows Chrome, 같은 9:16·60fps·standard, 둘 다 30초다. 두 렌더가 같은
조건이었다는 근거는 인코딩 버킷이다: `addSample`은 프레임 수와 해상도에만
좌우되고 패널 수와 무관한데 2812ms 대 2742ms로 **2.5% 이내 일치**한다.

| 버킷 | Day1(2패널) | Day1(4 video) | 배수 | 무엇에 비례하나 |
|---|---:|---:|---:|---|
| waitForReady | 7,334ms | 8,189ms | **1.12x** | 소스를 열고 디코더를 준비 (소스 3개→5개) |
| createFrame | 7,846ms | 12,538ms | **1.60x** | 프레임을 그림 — 패널 수가 실제로 드는 곳 |
| addSample | 2,813ms | 2,742ms | **0.98x** | H.264 인코딩 — 패널 수와 무관 |
| audioMixing | 77ms | 86ms | 1.12x | — |
| **합계** | **18.07s** | **23.55s** | **1.30x** | |

프레임당으로는 4.36ms → 6.97ms다. **핵심은 비용이 패널 수에 비례하지 않는다는
것이다**: 패널이 2배가 돼도 전체는 1.30배다. 인코딩은 아예 늘지 않고, 디코더
준비도 1.12배에 그치며, 패널 수에 실제로 반응하는 것은 프레임을 그리는
`createFrame` 하나(1.60배)뿐이기 때문이다. 30초 영상을 23.5초에 뽑으므로 실시간
보다 빠르다.

**M0 게이트 판정.** [M0 분석](../03-analysis/day1-quad.m0-perf-gate.md)은 VP9
대체 측정으로 **1.15배**를 예측했고 실측은 **1.30배**였다. 방향(패널 수에 대해
sub-linear, 4패널도 실용 범위)은 맞았지만 배수 자체는 13% 낙관적이었다. 대체
코덱 측정의 한계를 보여주는 기록이며, M0의 "게이트 통과" 결론 자체는 유효하다.

**관찰 — 비디오 캐시가 템플릿 전환을 넘어 유지된다.** Day1 렌더 로그에 blob이
7개 열려 있다(419MB). Day1은 패널 2개 + 엔드카드로 소스가 3개면 충분하므로,
직전 4분할 세션의 소스들이 @remotion/media 캐시에 남아 있다는 뜻이다. 이번
렌더는 정상 완료했고 캐시 용량도 일정하게 유지되므로 결함은 아니지만, 한
세션에서 템플릿을 여러 번 오가며 큰 소스를 다루면 메모리가 누적된다. 증상이
보이면(렌더 실패·탭 크래시) 새로고침이 즉효이고, 근본 해결은 별도 사이클감이다.

## 6. 남은 작업

배포(§5.2)와 실측(§5.2.1)이 끝나 이 사이클의 성공 기준은 모두 닫혔다. 남은 것은
이 사이클 밖의 항목이다.

1. **실제 Chrome에서 E2E 전량 실행** — `npm run test:e2e`. 운영자 실렌더로
   SC1·SC3·SC4를 실측 검증했으므로 급하지 않지만, 회귀를 자동으로 잡으려면
   여전히 필요하다 (개발 컨테이너에는 H.264가 없어 실행 불가)
2. **30초 용량 여유 19%** — 움직임이 많은 소재는 상한을 넘을 수 있다. 넘으면
   fps 30으로 대응 (§5.2.1)
3. **Remotion 라이선스 파라미터** — 렌더러가 `licenseKey` 없이 호출되어 매
   렌더마다 경고가 남는다. 평가 목적 사용은 Free License 범위라는 것이
   [라이선스 검토](../03-analysis/browser-video-mvp.remotion-license-review.md) §6의
   결론이므로 `'free-license'`를 명시해 경고를 없앨 수 있으나, 자격 주장이라
   운영자 판단 사항이라 손대지 않았다
4. **비디오 캐시 누적** — 템플릿을 오가면 이전 소스가 캐시에 남는다 (§5.2.1).
   새로고침이 즉효, 근본 해결은 별도 사이클감
5. **후속 사이클 후보** — 블러 배경 굽기. Day1 렌더 시간을 절반으로 줄이지만 픽셀
   동일성 검증이 따로 필요해 이번 범위에서 뺐다 ([Plan §2.12](../01-plan/features/day1-quad.plan.md))

> License가 필요하다는 조건은 이 사이클로 바뀌지 않았다.
